## Tier 3 — SQL Injection (CVSS 7.5–9.8)

Use GREP_RESULTS section `TIER3_SQL` (or `AUDIT_DIR/grep/group-sqli-results.md` in file-based mode). Also use `WPDB_LOOP_SQL_BUILD` to surface foreach loops over DB-fetched row variables in files containing `$wpdb->query` — primary detection signal for second-order SQLi in copy/duplicate functionality.

- Direct `$wpdb->query("... $variable ...")` without `prepare()` → SQLi
- `prepare()` with dynamically built format string → SQLi
- Variable interpolated despite `prepare()` being present → SQLi
- ORDER BY: `prepare()` wraps `%s` in quotes (broken for ORDER BY); plugins concatenate directly → SQLi. `%i` (WP 6.2+) safe.
- `%1$s` AND bare-numbered `%1s`/`%2s` (no `$`) placeholders are BOTH NOT auto-quoted (unlike bare `%s`) — verified WP 7.0 `class-wpdb.php::prepare()`: the add-quotes branch fires only when the format is empty (`'' === $format`), so ANY numeric prefix — with or without a trailing `$` — skips it; `allow_unsafe_unquoted_parameters` defaults `true`.
- `(int)` cast / `intval()` = legitimate integer defenses

**`esc_sql()` NOT a SQLi defense.** Only escapes quotes. Unquoted contexts (ORDER BY, LIMIT, OFFSET, GROUP BY, numeric WHERE) get zero protection. For LIMIT/OFFSET: only `intval()`/`absint()`/`(int)` cast is safe — `esc_sql()` and `sanitize_text_field()` pass numeric injection payloads unchanged.

**ORDER BY injection — most common WP plugin SQLi.** → See CANON:sanitize-text-field-limits, CANON:esc-like — neither prevents ORDER BY injection (values NOT quoted). Boolean-blind extraction: `ORDER BY (SELECT CASE WHEN (ASCII(SUBSTR(...))>64) THEN id ELSE title END)` — no quotes, no UNION. Correct defenses: allowlist, `sanitize_sql_orderby()`, or `%i` placeholder. Use GREP_RESULTS `ORDERBY_PARAMETER_HANDLING`. Cross-reference with `ADMIN_LIST_TABLES`.

**`esc_attr()` / `esc_url_raw()` NOT SQL defenses.** `esc_attr()` encodes `& < > " '` to HTML entities only — `1 OR 1=1` passes. `esc_url_raw()` validates URL structure but preserves `'` in path/query.

**`wp_unslash()` removes automatic SQL protection.** → See CANON:wp-magic-quotes. `wp_unslash()` = `stripslashes_deep()`. Use GREP_RESULTS `WP_UNSLASH_SQL_CONTEXT` and `WP_UNSLASH_BEFORE_SQL` (targeted: `wp_unslash()` wrapping superglobals in files with `$wpdb` calls).

**→ See CANON:esc-like.** Use GREP_RESULTS `ESC_LIKE_USAGE` — check: result → `prepare()` or string concat?

**IN() clause injection.** `explode()`/`preg_split()` into array placed directly in IN() without per-element `intval()` casting → each element injectable. Correct: `array_map('intval', $ids)` or `$wpdb->prepare()` with placeholder array or `wp_parse_id_list()`.

**SQL filter hook SQLi — invisible to `$wpdb->*` grep.** WP_Query and WP_Comment_Query both execute a final `$wpdb->query()` internally. Plugin callbacks on `posts_where`/`posts_join`/`posts_having`/`posts_orderby`/`posts_groupby`/`posts_clauses`/`comments_clauses`/`comment_feed_where`/`get_meta_sql` inject SQL fragments. Analysis: (1) find filter registrations (`SQL_FILTER_HOOKS` grep section — covers all of the above, including `comments_clauses`/`posts_clauses`); (2) read callback, trace captured variables (a class property set by a DIFFERENT method earlier in the request — e.g. an AJAX handler populating `$this->queryArgs[...]` before triggering the query — is a common second-order source the callback body alone won't show, per core SKILL.md FN Prevention #10); (3) check user-controlled values reach callback; (4) verify `prepare()` vs `esc_like()`/`sanitize_text_field()` only; (5) for `get_meta_sql`: `preg_replace()` replacement arg modifying `$sql['where']`/`$sql['join']` is a sink; for `comments_clauses`/`posts_clauses`/`get_meta_sql`, a direct `$args['where']`/`$args['join']` (etc.) concatenation-or-`.=` assignment of an uncast/unescaped value is the more common sink shape — Semgrep `claude.php.wordpress.sqli.sql-filter-hook-where-concat-unprepared` flags it structurally.

**`$_GET['s']` → WP_List_Table → `posts_where` canonical chain:** `$_GET['s']` → `sanitize_text_field()` → `esc_like()` → string interpolation → `posts_where` → WP_Query SQL. Neither strips quotes. If no `prepare()`, injectable.

**Two-path search / illusory safe path.** Standard search with `esc_like() + prepare()` ≠ safe conclusion. Advanced search modes (colon operators: `id:EMAIL`, `field:value`) frequently route through separate branch or cross-file helper without `prepare()`. After confirming standard path safe, grep for conditionals activating on special input patterns.

Use GREP_RESULTS `ADVANCED_SEARCH_PATHS`.

**`$wp_query->get()` / `get_query_var()` → raw SQL.** Rewrite-rule-derived query vars reach `$wp_query` via `parse_request()`. Percent-encoding the URL path prefix forces the `urldecode()` fallback match (class-wp.php:239), bypassing both `wp_magic_quotes()` and `WP_MatchesMapRegex` double-encoding — `parse_str()` decodes `%27` to a literal unescaped `'`. Plugins interpolating `$wp_query->get('slug')` into `$wpdb->get_var("...WHERE slug='$val'...")` without `$wpdb->prepare()` are injectable. Use GREP_RESULTS `WP_QUERY_VAR_SQL`.

**`$_COOKIE` values in SQL context.** Cookie values are fully attacker-controlled and bypass `wp_magic_quotes()` when read via `filter_input(INPUT_COOKIE, ...)`. Common pattern: quiz/session cookies storing comma-separated IDs flowing to `ORDER BY FIELD()` or `IN()` clauses via `sanitize_text_field()` only. Use GREP_RESULTS `COOKIE_SQL_INPUT` — surfaces `$_COOKIE` reads in files containing `$wpdb` calls.

**Shortcode `$atts` → SQL (Contributor+).** Shortcode attributes are contributor-controlled — any user with `edit_posts` can insert arbitrary attribute values in post content. When `$atts['param']` flows to `$wpdb` methods without `prepare()`, this is Contributor+ SQLi. Semgrep taint cannot cross file boundaries between `add_shortcode()` registration and callback definition — manual trace required. Use GREP_RESULTS `SHORTCODE_ATTR_SQL`.

**`sprintf()` as `prepare()` substitute.** `sprintf()` does NOT apply `mysqli_real_escape_string()` to `%s` arguments — string values interpolated raw. Use GREP_RESULTS `SPRINTF_SQL_BUILD`. Also use `CONCAT_ASSIGN_SQL_BUILD` to surface `.=` query string construction in files with `$wpdb` calls. The `sprintf()` call frequently builds only a WHERE-clause FRAGMENT assigned to a variable, spliced into a separately-built query string one or more statements later (via `.` concatenation or `{$var}` interpolation) rather than passed as a literal inline sink argument — trace the assigned variable forward to its actual query-building use before concluding it's unreachable.

**Additional grep sections for Tier 3:** `ESC_ATTR_SQL_CONTEXT` (esc_attr near SQL keywords in files with `$wpdb`), `ESC_URL_RAW_SQL_CONTEXT` (esc_url_raw in files with `$wpdb`), `FILTER_INPUT_SQL_CONTEXT` (filter_input in files with `$wpdb`).

## Beyond literal `$wpdb->` — sink & defense gaps

These patterns recur in recent disclosures and are *missed by detection that keys only on the literal `$wpdb->` receiver or that trusts any `prepare()` call.* Each names its GREP_RESULTS section + Semgrep rule (the detection) — the prose is the ≤2-sentence reasoning. See `docs/sqli-research-2026.md` for citations.

**Aliased / wrapper `$wpdb` sinks.** Every standard SQLi signal matches `$wpdb->…`. Plugins routinely stash the global in an object property (`global $wpdb; $this->wpdb = $wpdb;`) or in `$GLOBALS['wpdb']`, then run queries via `$this->wpdb->`, `$this->db->`, `$this->database->`, or `self::$db->` — **invisible to `$wpdb->` grep/semgrep**. Empirically the dominant form (338+ corpus hits; e.g. better-search-replace `BSR_DB` → `$this->wpdb->get_var("…$table…")`). When a plugin's whole SQL layer is wrapper-based, these sections are the *only* ones that surface it. Use GREP_RESULTS `WPDB_WRAPPER_SQL` + semgrep `wpdb-wrapper-property-user-input-taint`. Confirm the property actually holds `$wpdb` (constructor assignment) and that user input reaches a dynamic (interpolated/concatenated) query. Note: `$this->db` may instead be a raw `mysqli`/PDO handle — still a SQL sink; check whether its own escaping/placeholders are used.

**User input as the `prepare()` format string.** `prepare()` escapes only the values bound to `%s/%d/%f/%i`; bytes in the **first argument** (the format/query string) are emitted verbatim (verified WP 7.0 `class-wpdb.php::prepare()` — a missing placeholder only raises a `_doing_it_wrong` notice, the query still runs). So all of these are injectable *despite* `prepare()`: `$wpdb->prepare($_GET['q'])` (whole string), `$wpdb->prepare("… FROM $userTable WHERE id=%d", $id)` (interpolation), and concatenation into the format string. The generic taint rule treats `prepare()` as a *sanitizer*, so this is its blind spot. Use GREP_RESULTS `PREPARE_USER_INPUT_FORMAT_STRING` + semgrep `wpdb-prepare-user-input-format-string`. **Do NOT report** legacy nested/"double-prepare" re-quoting — Core mitigated it (stray `%` are escaped); the live class is user input *in the format string*.

**Custom query-builder objects.** Plugin ORMs / bundled Illuminate/Doctrine expose `->where()/->order_by()/->having()/->select()/->join()` and raw-fragment methods `whereRaw`/`orderByRaw`/`havingRaw`/`selectRaw`/`groupByRaw` (also seen snake_case — `where_raw`/`having_raw` — or raw-prefixed — `rawWhere`/`raw_where`). Raw-fragment methods accept literal SQL; ordinary builder methods fed a superglobal interpolate it. Per-value `prepare()`-style binding on a *later* argument does NOT protect the fragment TEXT itself passed as the first argument — a request-controlled fragment reaching `whereRaw($fragment)`/`havingRaw($fragment)` unguarded is injectable regardless of any bound-values array; the only sound fix is validating the fragment's exact (whitespace-normalized) text against an allow-list of values legitimately declared elsewhere in the plugin and splicing the matched canonical string, never the attacker-supplied one. All bypass `$wpdb->` greps. The vulnerable call often spans several method calls from the `$_POST` read, so semgrep taint mode cannot trace it — the rule matches the sink shape structurally and is lead-generation only. Use GREP_RESULTS `SQL_QUERY_BUILDER_METHODS` + semgrep `raw-where-fragment-unprepared-query-builder`; trace the builder to its final SQL emission and confirm the fragment TEXT (not just bound values) is allow-listed.

**Hand-rolled PDO-style named-placeholder binder.** A custom DB wrapper splices `wpdb->prepare()`'d values into a `:placeholder` query template via `str_replace()` inside a loop that reassigns the query string each iteration — sequential, not atomic. A bound string value containing another placeholder's literal name survives its own (correctly quoted) substitution and gets rematched by that placeholder's later iteration, splicing a quote pair into the string literal it sits in — SQLi despite every value passing through `prepare()`. Only a single simultaneous `strtr()` pass over the original template is safe; array-form `str_replace()` is still sequential internally. Use GREP_RESULTS `SELF_REASSIGN_STR_REPLACE_SQL_BUILD` + semgrep `custom-orm-sequential-placeholder-replace`.

**Filter/condition array KEY trusted as SQL identifier.** A custom query-builder's WHERE-condition constructor iterates a filter/condition array and concatenates the loop's KEY (not its value) onto a column identifier to form a new condition, while the paired value is safely bound — but the key itself is never checked against an allow-list of permitted comparison operators/columns before concatenation. Only the value is protected; the key becomes a raw SQL fragment. If the key can be shaped by request-supplied array structure (nested query-string arrays, JSON body fields) rather than always being a plugin-chosen literal, this is SQLi through the identifier position while the escaped value hides it. Use GREP_RESULTS `DYNAMIC_WHERE_KEY_CONCAT` + semgrep `dynamic-where-array-key-as-operator`; confirm the key's origin traces to attacker-influenced input, not a hardcoded literal.

**Already-quoted IN() list re-wrapped in an extra literal quote pair.** A helper builds a comma-separated `IN()` list with each element individually quoted/escaped (a custom "build a safe IN clause" function, or an inline `$wpdb->prepare('%s', ...)`/`esc_sql()` map) — safe on its own — but the call site then concatenates that already-quoted list into the raw SQL string wrapped in one more pair of literal single quotes: `"... IN ('" . $list . "')"`. The leading adjacent quote pair collapses into an empty-string SQL token, exposing the rest of the first list element as unquoted, executable SQL — boolean/UNION injection despite every value having been individually escaped. Only fires when the extra quotes sit directly against the `IN( ` / `)` boundary; removing them (`IN ({$list})`) or integer-casting every element (`array_map('absint'/'intval', ...)`) before the list is built are both sufficient fixes. Use GREP_RESULTS `WPDB_IN_CLAUSE_DOUBLE_QUOTE_WRAP` + semgrep `wpdb-in-clause-double-quote-wrap`.

**`order` direction (ASC/DESC) is its own injection point.** ORDER BY review must check the **direction** param (`order`) as well as the **column** (`orderby`). A correct allowlist asserts `order` ∈ {asc, desc} AND `orderby` ∈ {known columns}; plugins commonly guard one and interpolate the other (Trustwave: 4/5 studied plugins vulnerable in `order` and/or `orderby`). `sanitize_text_field()` protects neither.

**Numeric context "assumed integer, never cast."** `… WHERE id = $id` / `IN ($id)` / `LIMIT $n` (unquoted) with `$id` from input but only `sanitize_text_field()` or `esc_sql()` applied is injectable — no quote is needed, so quote-escaping does nothing. Only `(int)`/`intval()`/`absint()` defend an unquoted numeric position. Recurs where a REST/AJAX param is "assumed numeric" and in IPN/webhook IDs (`$_POST['custom']` → `WHERE id = {$id}`). Treat every unquoted `= $var` as integer-only. Exception: if the value is instead used only as an operand of a PHP arithmetic operator (`*`, `+`, `-`, `/`) before reaching the sink — e.g. `$offset = $page * $limit` — PHP's own numeric type-juggling coerces a non-numeric-prefixed string operand to a number as a side effect of the operation, neutralizing it the same as an explicit cast; this only protects the arithmetic RESULT, not the original variable if it is also used unmodified elsewhere in the same query.

**Raw complete SQL statement accepted as a first-class parameter (not a value/fragment).** Some plugins — most commonly "remote management"/"data export"/"custom report" style features — expose an API/settings parameter (commonly named `query`, `sql`, `sql_query`, `raw_query`) whose value IS the entire SQL statement text, passed directly to `$wpdb->query()`/`get_var()`/`get_results()`/`get_col()`/`get_row()` with zero transformation of any kind — not even the `esc_sql()`/`prepare()` treatment a fragment or value would normally receive, because the parameter's own design accepts "a query" rather than "a value to inject into a query." This is strictly more dangerous than typical injection since no boundary character needs to be broken out of, and it enables arbitrary non-SELECT statements (UPDATE/INSERT/DELETE/DROP) through what may present as a read-only "reporting"/"diagnostics" feature. Grep for array/parameter keys literally named `query`/`sql`/`raw_query` flowing directly into any `$wpdb`-style execution method with no wrapping function call at all — see grep section `RAW_QUERY_KEY_SQL` and semgrep `raw-query-key-unprepared-wpdb-execution`.


## Group SQLi — FP Verification Rules

These rules supplement the universal FP rules in the shared core SKILL.md Phase 4.

21. **SQL via `$wp_query->query_vars`:** Confirmed injectable via percent-encoded URL prefix bypass (see Phase 1B). When plugin interpolates `$wp_query->get()` into raw SQL without `$wpdb->prepare()`, verify rewrite rule exists for the query var and the code path reaches the SQL sink.

22. **Wrapper-sink (`WPDB_WRAPPER_SQL` / `wpdb-wrapper-property-user-input-taint`):** before reporting, confirm (a) the property/handle is `$wpdb` or a raw DB connection (read the constructor / assignment), (b) the query is *dynamic* — interpolated, concatenated, or a pre-built `$sql` var, not a literal — and (c) user input reaches it. A wrapper method that internally `prepare()`s every value, or builds only from hardcoded strings / DB reads, is a FP.

23. **`prepare()` format-string (`PREPARE_USER_INPUT_FORMAT_STRING` / `wpdb-prepare-user-input-format-string`):** TP only when the *dynamic* portion of the first argument is user-controlled and unbounded. FP if that portion is an allowlisted token (`in_array`/`switch`) or already `intval()`/`sanitize_key()`/`sanitize_sql_orderby()`d before interpolation — Semgrep cannot see the branch. User input passed solely as a `%s/%d` *value* argument (not in the format string) is safe and must not be reported.

24. **Parameterized query with an attacker-controlled key/value matching across OTHER users' or sessions' rows:** ruling out SQL syntax injection (proper `%s`/`%d` binding) does not end the analysis — if the matched row set is not scoped to the requester's own identity/session, and the requester can choose both the compared value AND the field/column being compared (e.g. via a JSON path or dynamic column built from a request key), this is a cross-user existence/disclosure primitive for Group D1/AC to assess. Forward it as a lead (see GREP_RESULTS `JSON_PATH_DYNAMIC_KEY_LOOKUP`) rather than closing it as "not SQLi."

25. **Shared upstream sanitizer protects multiple downstream repositories/endpoints.** A repository interpolating `orderby`/`sort_by` directly into DQL/SQL with no per-field allowlist of its own is not automatically injectable — a shared base-class/handler method (e.g. a listing-controller's `sanitizeSortBy()`) may already character-class-restrict the value for every caller before it reaches the repository. Trace the actual caller chain to the real entry point's sanitization before confirming, rather than assuming each repository independently guards the parameter.

26. **Arguments-array key as an opt-in raw WHERE-fragment passthrough (`RAW_WHERE_ARRAY_KEY_PASSTHROUGH` / `raw-where-key-concat-no-sanitizer`):** distinct from a whole-statement `query`/`sql` parameter (rule above) and from the identifier-position key (rule 21-style) — here a custom WHERE-builder's arguments array has one key (naming pattern: "where" + "sql"/"raw") whose *value* is concatenated verbatim onto the accumulator with zero wrapping call of any kind, intended only for trusted code-level callers. TP unless the same key is explicitly rejected when it arrives directly from `$_GET`/`$_POST`/`$_REQUEST` before the concatenation runs.

27. **ORDER BY allow-list mixing key-based and value-based membership checks (`ORDERBY_ALLOWLIST_KEY_VALUE_CONFUSION` / `orderby-foreach-key-value-allowlist-confusion`):** an `elseif (array_key_exists($key, $allowed))` branch beside a sibling `in_array($value, $allowed)` branch on the same list is a TP only when `$allowed` is a plain list array (`array_keys()`/`array_merge()`, no explicit string keys) — integer keys then exist regardless of value, so an attacker-supplied indexed array bypasses validation entirely. A hand-written associative shortcut map (`'id' => 'event_id'`) or a branch already guarded by `!is_numeric($key)`/`is_string($key)` is a FP.

28. **SELECT column-list identifier position, distinct from ORDER BY (`REQUEST_FIELDS_RAW_SELECT_COLUMN_LIST` / `unvalidated-request-fields-select-column-list`):** a request-controlled "fields"/"columns" array imploded and interpolated bare into `SELECT $var FROM` is a TP unless each element was checked against a real allow-list (schema-derived `SHOW COLUMNS` or a hardcoded `in_array`/`array_intersect` list) before the implode — a bare `$wpdb->prepare()` call with no placeholder bound to that value is a no-op here and must not be treated as a sanitizer (rule 22-style).

29. **`WP_Query`/`WP_Term_Query`/`WP_Comment_Query` `orderby`/`order` constructor args are safe regardless of the plugin's own (in)sufficient validation.** All three classes' internal `parse_orderby()`/`parse_order()` enforce their own strict allowlist (or a hardcoded fallback) before any SQL is built — an unsanitized value passed straight through to these args is not a finding. Only report when the value instead reaches a raw `$wpdb` fragment or a `posts_orderby`/`posts_where`-style filter hook, bypassing Core's parser entirely.
   - The same trust extends to WooCommerce's `wc_get_orders()`/`WC_Order_Query`: scalar constructor args (`billing_email`, `customer_id`, `post__in`, `limit`, `orderby`) are validated/escaped internally regardless of the plugin's own sanitization of the value passed in. Only a raw `meta_query`/`date_query` fragment built by string-concatenating unsanitized input bypasses this.

30. **Pre-quoted `'%s'`/`"%s"` placeholder in `prepare()` is not a double-quoting bug.** WP core's `prepare()` strips the literal quotes surrounding a bare `%s` placeholder and re-adds them consistently before binding (verified `class-wpdb.php::prepare()`, backward-compat behavior) — this does NOT apply to numbered placeholders (`%1$s`), which are emitted as-is if hand-quoted, so only flag those.
   - The same auto-quoting neutralizes a BARE, unnumbered `%s` with no quote characters in the template at all (e.g. inside `IN(%s)`) — WP core wraps it in quotes regardless, making this a functionality bug (the whole list becomes one quoted string, not multiple bound values) rather than SQLi. Only a NUMBERED bare placeholder (`%1s`, no `$`) skips the auto-quoting, same exception as the parent rule.
