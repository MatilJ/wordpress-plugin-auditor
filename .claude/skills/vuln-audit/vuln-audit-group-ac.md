# Vuln-Audit Group AC — Access Control: Missing Authorization, IDOR, CSRF

> Authorized Wordfence bug-bounty research (see `AUTHORIZATION.md`). Loaded alongside core `SKILL.md`. Runs in the early access-control band (right after Auth-Bypass). Read checkpoint-foundation.md and checkpoint-group-ab.md, auth-model.md + foundation.md (Foundation phase), and leads-forward.md before starting. This group FILLS the `CIA Impact` and `Verdict` columns of the auth-model Handler Auth Summary.

> **OOS Auth Floor Gate (current program policy):** If the auth floor for a finding resolves to Contributor (`edit_posts`) or Author (`publish_posts`), the finding is **OOS / bounty-ineligible**. Do NOT write it to findings.md. Record it in the checkpoint file as "OOS — mid-level auth (Contributor/Author)." Exception: if a chain lowers the effective auth floor to Subscriber or Unauthenticated, confirm the chain at the lowered floor. SSRF (CWE-918) is also OOS regardless of auth floor.

## Tier 4 — Broken Access Control / Privilege Escalation (CVSS 7.0–9.8)

For every AJAX handler, `admin_init` hook, and `handle_bulk_actions-*` filter callback:

```
Layer 1 — CAPABILITY: current_user_can() present? Which cap? Missing → Subscriber access, but see Layer 4 — `admin_init` handlers default to UNAUTHENTICATED reachability, not Subscriber. Use `ADMIN_INIT_SUPERGLOBAL_READS` grep results to surface admin_init handler bodies reading GET/POST parameters without capability gates — these are the highest-priority admin_init handlers to audit for Missing Authorization.
Layer 2 — NONCE: wp_verify_nonce() present? Trace nonce creation: admin page (gated) / public page (theater) / admin_notices (Subscriber sees on profile.php) / admin_enqueue_scripts without cap check (all logged-in users) / page builder editor (edit_posts = Contributors)
Layer 3 — INPUT: Even with auth+nonce, trace input to sinks.
Layer 4 — REACHABILITY: Cross-reference against custom role/capability map. Self-obtainable role → functionally open. For `admin_init` handlers: `/wp-admin/admin-ajax.php` fires `do_action('admin_init')` UNCONDITIONALLY, before the `is_user_logged_in()` branch that selects `wp_ajax_{action}`/`wp_ajax_nopriv_{action}`, and it never calls `auth_redirect()` — so any `admin_init` callback whose registration path is reachable without login (an unconditional `add_action('admin_init', ...)`, or one gated only by a self-obtainable nonce/GET-param check evaluated during `plugins_loaded`/`init`, both of which also fire on every `admin-ajax.php` hit) is reachable by a fully UNAUTHENTICATED request to `admin-ajax.php?action=<any_non_empty_value>` — default floor is Unauthenticated (PR:N), not Subscriber. The exception: a handler registered ONLY inside an `admin_menu` callback is NOT reachable via `admin-ajax.php` (which never fires `admin_menu`) — that case genuinely requires visiting a regular `/wp-admin/` page like `profile.php` (Subscriber, `read` capability), since reaching `admin_menu` itself requires login.
```

**Bulk action handlers (`handle_bulk_actions-{screen}`):** WordPress Core verifies the bulk-action nonce and enforces the page-level capability before the filter fires, but the callback receives whatever item IDs the user submitted — no per-item ownership filtering. The callback must enforce `current_user_can()` for the intended privilege level. Auth floor = the page's required capability (e.g., `edit_posts` for `edit-comments.php` = Contributor+, `list_users` for `users.php` = Administrator). Use GREP_RESULTS `BULK_ACTION_HANDLERS`. For each `handle_bulk_actions-*` registration: (1) read callback body for `current_user_can()`; (2) if absent, determine auth floor from the screen's page-level capability; (3) if auth floor ≤ Contributor, confirm CIA impact — data export (PII, non-public content) or write operations on arbitrary IDs = confirmed finding.
   - **`load-{screen}.php` hook as equivalent bulk-action surface:** Plugins may register `add_action('load-edit.php', ...)` (or `load-users.php`, `load-edit-comments.php`, etc.) to intercept bulk actions by reading `$_REQUEST['action']` directly instead of using the `handle_bulk_actions-*` filter. **Correction:** these hooks do NOT fire "at the page's capability floor" — → See core "WordPress Route → Hook → Auth Quick Reference": `wp-admin/admin.php`'s core-file dispatch calls only `auth_redirect()` before firing `load-{$pagenow}`; the page's own capability check runs later, in the page's own script. So a `load-{screen}.php` callback's real floor is "any authenticated user," and the page-level bulk nonce (issued to all users who pass the PAGE's later gate) does not authorize ownership of submitted item IDs either. Apply the same per-item ownership check analysis as for `handle_bulk_actions-*` handlers; use GREP_RESULTS `LOAD_SCREEN_HOOKS`.
   - **`load-{page}.php` / `admin_action_{action}` hook performing a direct write/delete (not just bulk-action interception):** The same missing-pre-dispatch-gate fact applies to ANY write reachable from these hooks, not only bulk-action item processing — e.g. a `load-post.php` callback that resolves an object ID from `$_GET`/post meta and calls a delete/update sink with no `current_user_can()` of its own is Missing Authorization at a Subscriber floor, exploitable via a normal page request (`GET /wp-admin/post.php?post=<id>&action=edit`) regardless of what capability that admin screen would otherwise require. Use GREP_RESULTS `ADMIN_ACTION_HOOKS` for `admin_action_*` registrations (the AJAX-sibling dispatch family sharing the same `admin.php` bootstrap) alongside `LOAD_SCREEN_HOOKS`.

**ANTI-RATIONALIZATION — STRICTLY ENFORCED:**
Do NOT dismiss nonce-only handlers (no `current_user_can()`) with any of these rationalizations:
- "Intentional behavior" — irrelevant. Missing auth = missing auth regardless of developer intent.
- "Functionally equivalent to what the role can already do" — WRONG. A Contributor can create draft posts but CANNOT publish. `wp_insert_post()` with `'post_status' => 'publish'` bypasses `publish_posts` capability. Any CPT post creation at a status the user lacks capability for = confirmed finding.
  - **CPT capability map:** `register_post_type()` with `capability_type => ['slug','slugs']` or explicit `capabilities` array remaps `publish_posts` to `publish_slug` (admin-only); `wp_insert_post()` does not enforce this remapped cap. Use GREP_RESULTS `CPT_CUSTOM_CAPABILITIES` — a handler checking `current_user_can('publish_posts')` is a false auth gate for any CPT with a custom publish capability mapping. Also use `CPT_PAGE_CAPABILITY_TYPE` to surface CPTs using `capability_type: 'page'` (the most common silent remapping — maps `edit_posts` → `edit_others_pages` and `publish_posts` → `publish_pages`, both Editor+).
  - **CPT read-listing gap:** `get_posts()` and `new WP_Query()` also do not enforce CPT capability arrays — only the WP REST API router does. A REST/AJAX handler accepting a user-supplied `post_type` and passing it to `get_posts()`/`WP_Query` without an explicit allowlist discloses any registered CPT regardless of configured capabilities. Use GREP_RESULTS `REST_POST_TYPE_PARAM`.
- "The nonce is hard to obtain" — nonce availability analysis determines auth FLOOR, not dismissal.
- "Low impact / internal posts" — impact assessment happens AFTER confirmation, not instead of it.
- "The action is read-only" — verify this claim. If handler calls `wp_insert_post`, `wp_update_post`, `wp_publish_post`, `update_option`, `update_post_meta`, `wp_delete_post`, `wp_trash_post`, `wp_delete_comment`, `wp_insert_comment`, `wp_update_comment`, `wp_new_comment`, `wp_trash_comment`, `wp_delete_term`, `wp_set_object_terms`, `wp_set_post_terms`, `set_post_thumbnail`, `delete_post_thumbnail`, `wp_delete_user`, `wp_delete_attachment`, `delete_option`, `delete_site_option`, `$wpdb->delete()` → it is NOT read-only.

**Mechanical rule:** If `check_ajax_referer()`, `check_admin_referer()`, or `wp_verify_nonce()` on an `init` hook handler is present but NO `current_user_can()` call exists before the first write operation (any write sink listed under the "The action is read-only" rationalization above, plus `delete_transient`/`delete_site_transient`) → CONFIRMED Missing Authorization. Report it. Determine auth floor from nonce availability, then assess CVSS. When the handler body contains only a nonce check and a single delegated method call with no write sinks directly visible, read the called method's source (and its own callees) before concluding the handler is non-writable — nonce-only + delegated writes is equally exploitable as nonce-only + inline writes. This rule also applies to read-only handlers: a nonce-only `wp_ajax_` handler returning non-public post content (`post_content`, template renders with post data) without `current_user_can('read_post', $id)` or `post_status === 'publish'` gate is Missing Authorization for information disclosure (CWE-862 + CWE-200).

**Dependent-field "context" value used as an unvalidated meta-key lookup:** Auto-update/cascading-select/conditional-field generators that regenerate one field's options from another field's current value commonly pass that value through as a literal `meta_key` (or `get_post_meta()`/`get_user_meta()` key argument) with only generic content sanitization (`sanitize_text_field()`/`sanitize_key()`/`trim()`) — none of which restrict WHICH key can be requested. If the read is a bulk/table-wide query (not scoped to an already-authorized object ID) and no server-computed `in_array($key, $allowed_keys, true)` allow-list gates it, an unauthenticated or low-privileged caller can enumerate every distinct value stored under an arbitrary meta key sitewide, including PII in underscore-prefixed keys never shown in any UI. Use GREP_RESULTS `DEPENDENT_FIELD_CONTEXT_META_KEY`.

**False-safe gate before `wp_new_comment()`/`wp_insert_comment()`:** `comments_open( $post_id )` checks only the target post's `comment_status` field — never `post_status`, `post_password`, or the caller's capability. A handler that calls `comments_open()` immediately before a comment-write sink and treats that as "the check" is not authorized: apply the Mechanical rule above unchanged (the sink still requires `current_user_can('read_post', $id)` plus the private/trash/draft-pending-future/`post_password_required()` checks WP Core's own `wp_handle_comment_submission()` performs). Use GREP_RESULTS `NOPRIV_COMMENT_READS` for the read-side analog: a nopriv/AJAX handler calling `get_comments()` for a post's comments needs the same `post_status === 'publish'` AND `post_password_required()` gate as any other content-read path — a `'publish' !== $post->post_status` check alone still passes for password-protected posts (see the WC_AJAX_HOOKS analysis note in core SKILL.md).

**Missing Authorization — Common Vulnerable Patterns (CVE-grounded):**

These patterns represent the most frequently exploited Missing Authorization variants in WordPress plugins. For each, the detection workflow is: (1) identify the hook/entry point; (2) trace to the handler body; (3) check for `current_user_can()` before the first write sink; (4) if absent, determine auth floor from hook type and nonce availability.

**`admin_post_nopriv_` handlers — identical analysis to `wp_ajax_nopriv_`:** WordPress processes `admin_post_nopriv_{action}` via `/wp-admin/admin-post.php` for unauthenticated visitors (and `admin_post_{action}` for authenticated). Both load `wp-load.php` but do NOT load the admin menu or enforce any capability beyond what the handler itself checks. The naming convention (`admin_post`) misleads developers into assuming admin context — it provides no admin-level protection. Every `admin_post_nopriv_` handler requires the same 4-layer audit as `wp_ajax_nopriv_` handlers. Use GREP_RESULTS `NOPRIV_OPTION_WRITES` and `NOPRIV_USER_WRITES` to surface high-impact writes in these handler files.

**Shortcode callbacks — Contributor+ attack surface:** Shortcode callbacks execute when WordPress renders post content containing `[shortcode_tag]`. Any user with `edit_posts` (Contributor+) can insert arbitrary shortcode tags and attributes into draft post content — the shortcode callback runs during preview rendering. Use GREP_RESULTS `SHORTCODE_PRIVILEGED_OPERATIONS` to surface write operations in shortcode callback files. For each hit: (1) find the `add_shortcode('tag', 'callback')` registration; (2) read the callback body; (3) if it calls `wp_insert_post()`, `update_option()`, `wp_mail()`, `wp_remote_post()`, or `$wpdb->insert()` without `current_user_can()` → Contributor+ Missing Authorization. Shortcode attributes (`$atts`) are fully attacker-controlled and unsanitized — apply the same distrust as `$_POST` values.

**`init` / `wp_loaded` / `template_redirect` handlers with state changes:** These hooks fire on every front-end AND back-end request. Handlers commonly implement custom routing by checking `$_GET['action']` or `$_POST['action']` to dispatch to sub-functions. The dispatch check itself (`isset($_GET['action']) && $_GET['action'] === 'my_action'`) is NOT an authorization gate — it only determines which code path runs. Use GREP_RESULTS `INIT_HOOK_STATE_CHANGES` to surface write sinks in these handler files. For each: (1) trace from the hook registration to the callback; (2) determine whether any request parameter gates the write path; (3) check for `current_user_can()` before the write — if absent, the endpoint is unauthenticated. Common false positive: handlers that check `is_admin()` — this returns `true` when the request URL starts with `/wp-admin/` but does NOT verify user authentication or capabilities. Cross-reference with GREP_RESULTS `BROKEN_AUTH_LOGIC` to identify `is_admin()` misuse in the same files.

**Broken `&&` short-circuit:** `if (!is_user_logged_in() && !current_user_can('manage_options'))` — for logged-in users, first operand false → `&&` short-circuits → `current_user_can()` never evaluates. Use `||`. Use GREP_RESULTS `BROKEN_AUTH_LOGIC`.

**NONCE AVAILABILITY — mandatory verification:** → See CANON:nonce-verification. Check CPT `show_in_menu => 'parent-slug'` → WordPress enforces PARENT menu capability. `admin_enqueue_scripts` callback without `current_user_can()` before `wp_create_nonce()` = nonce injected for ALL authenticated users on any admin screen loading the script. `enqueue_block_editor_assets` without `current_user_can()` = nonce available to all `edit_posts` users (Contributor+); any plugin that localizes a nonce inside a function hooked to `enqueue_block_editor_assets` without a post-publish-status guard exposes that nonce to Contributors. If the callback checks `get_post_status()` for `'publish'` before nonce creation, the auth floor rises to Author (Contributors lack `publish_posts` and cannot edit published posts) — always read the full callback body. Use the `PAGEBUILDER_HOOKS` grep section to identify functions registered on page builder editor hooks (Elementor, Beaver Builder, etc.) — treat these identically to `enqueue_block_editor_assets` for nonce availability analysis. Dashboard widgets registered via `wp_add_dashboard_widget()` (typically inside a `wp_dashboard_setup` callback) render on `/wp-admin/index.php`, which requires only the `read` capability — a nonce emitted inside the widget's render callback without its own `current_user_can()` check is Subscriber-floor, identical to the `admin_notices` case. **Admin-only emission → OOS:** if EVERY emission site of the verified action string requires a capability the attacker role lacks (e.g., `wp_create_nonce()` only inside `manage_options`-gated callbacks/pages), the attacker cannot obtain a session-valid nonce (nonces are uid/token-bound; an admin-minted nonce will not validate for a Subscriber) — the nonce is de-facto authorization, so raise the auth floor to that capability and treat an Editor/Admin floor as OOS (defense-in-depth), unless a nonce-vendor endpoint mints it for the attacker role — either a REST route (`REST_NONCE_EXPOSURE`) or an equally-valid sibling `wp_ajax_*`/`wp_ajax_nopriv_*` handler with no capability/nonce check of its own that mints or returns the same action string's nonce (cross-check every handler in the plugin's own Nonce Availability table, not just REST hits). This does NOT dismiss genuine nonce-theater: when an emission site IS reachable at the attacker's role, the missing `current_user_can()` remains a confirmed finding.

**DISPATCHER CONSISTENCY:** Plugins routing multiple sub-actions through single handler commonly enforce global minimum cap at entry + per-item auth (e.g., `checkImageAccess($item)`) in each branch. When per-item auth is missing in one branch while present in N-1 siblings → exploitable. Read all `case`/`elseif` branches; identify per-item auth call; verify each branch performing writes calls it.
   - Also verify per-branch **capability** checks when nonce verification is centralized before the switch: a function that calls `wp_verify_nonce()` once at the top and applies `current_user_can()` per-branch may have individual `case`/`elseif` branches that return or delegate to a write function before reaching any capability check — the nonce is self-generatable by any Subscriber+ (→ See CANON:nonce-verification), so nonce-only branches in an otherwise admin-gated dispatcher are exploitable at Subscriber level.

**Unauthenticated nonce behavior:** UID 0 visitors share same nonce within 12 hours. Public page nonce = CSRF protection only, not auth.

**For REST endpoints:** → See CANON:rest-permission-callback. Also: `permission_callback => function() { return is_admin(); }` blocks ALL REST access (bug, not security). Custom routing layers wrapping `register_rest_route()`: read dispatch mechanism to verify actual `permission_callback`. Use GREP_RESULTS `REST_LOGIN_ONLY_PERMISSION` to surface `is_user_logged_in()` (and its common re-implementation, `get_current_user_id()` compared against `0`, which the base function name alone does not signal) in files containing `register_rest_route` or `permission_callback` — base route classes commonly define shared methods wrapping only a login check without `current_user_can()`, and individual routes may inconsistently reference the login-only method instead of the capability-checking method. Use GREP_RESULTS `REST_NONCE_ONLY_PERMISSION` to surface `wp_verify_nonce($X, 'wp_rest')` calls with no accompanying `current_user_can()` — the same shared-base-class pattern applies to nonce-only permission methods: `wp_verify_nonce(..., 'wp_rest')` proves session validity, not capability, and WP Core mints that nonce for every authenticated role (see CANON:nonce-verification).

**Reflection-based `permission_callback` auto-wiring:** Some custom routing frameworks decide which `permission_callback` to attach per route by using PHP Reflection to check whether the concrete route class itself declares an override of a capability-checking method (e.g. `$reflection->getMethod($method)->class === get_class($this)`, or the equivalent `getDeclaringClass()->getName()` form). `ReflectionMethod::$class`/`getDeclaringClass()` always returns the class where the method is *textually declared* — if that capability-checking method lives on an intermediate/abstract base class one or more levels above the concrete route classes and is never redeclared in them, the comparison is always false for every one of those routes, and the framework silently falls back to a weaker default (commonly login-only) for all of them regardless of what the base class's method appears to enforce. Use GREP_RESULTS `REST_REFLECTION_PERMISSION_WIRING` to surface `->class`/`getDeclaringClass()` comparisons in files containing `register_rest_route` or `permission_callback`; for each hit, read every concrete route class in the same module and confirm whether it redeclares the compared method itself — if none do, every route resolving through that check is running the fallback callback, not the intended one, regardless of an in-handler compensating check on some sibling routes.

**REST METHOD TIER CONSISTENCY:** In controllers extending `WP_REST_Controller`, `permissions_check()` is the fallback gate for all HTTP methods lacking a dedicated callback — when `update_item_permissions_check()` requires `manage_options` but `create_item_permissions_check()` / `delete_item_permissions_check()` are absent, POST and DELETE operations fall back to the weaker `permissions_check()` gate. Use REST_PERMISSION_CHECK_HAS_CAP grep section to surface `->has_cap('edit_*')` in permission check methods; CPT post type object `has_cap()` calls are not captured by TIER4_CAPABILITY_CHECKS (which covers only the `current_user_can()` function).

**List-tier permission check reused on a mutating route:** `get_items_permissions_check()` is the WP_REST_Controller convention for gating a read-only collection listing, and plugins commonly let it accept a weaker proof of access than a write/delete warrants (a site-wide API token, a public-widget nonce, a lower capability) — appropriate for browsing, not for triggering a state change. Wiring that same callback to a POST/PUT/PATCH/DELETE `register_rest_route()` entry silently inherits the weaker bar for the mutating action. Use GREP_RESULTS `REST_ITEMS_PERM_ON_WRITE_ROUTE` to surface `permission_callback => array($this, '...get_items_permissions_check')` in files that also reference a mutating HTTP verb (`WP_REST_Server::CREATABLE`/`EDITABLE`/`DELETABLE` or raw `POST`/`PUT`/`PATCH`/`DELETE`) — the grep is file-level, not per-route, so also check GET routes whose callback has destructive side effects (purge/reset/bulk-delete) that a verb-only check would miss. For each hit, confirm the route's HTTP method is actually mutating (or destructive-despite-GET) and read `get_items_permissions_check()`'s body: a bare `current_user_can()` with no token/nonce fallback is a false positive; any branch that returns true from a static/global token comparison or an unguarded nonce check is the real bug.

**Single-item permission check missing the collection route's context gate:** WP REST schemas commonly restrict sensitive fields (email, IP address, internal notes, tokens) to `'context' => ['edit']` so `filter_response_by_context()` strips them under the default `view` context — that redaction is a data-shaping step, not authorization. When `get_items_permissions_check()` proves the plugin intended `context=edit` to require an elevated capability (e.g. `'edit' === $context && !current_user_can('edit_posts')`), but the sibling `get_item_permissions_check()` (the single-resource route) never inspects `context` at all, a caller who only satisfies the item's own weaker read check can still pass `?context=edit` on the single-item route and receive the edit-only fields anyway. Use GREP_RESULTS `REST_ITEM_PERMISSION_NO_CONTEXT_CHECK` to surface `get_item_permissions_check()` definitions in files that also define `get_items_permissions_check()`. For each hit: (1) confirm the item schema actually restricts a sensitive field to `context=edit`; (2) read `get_items_permissions_check()` for the context+capability gate and confirm `get_item_permissions_check()` lacks it (directly, and not via a shared helper both methods call); (3) confirm the item check's own read requirement is satisfiable by a lower-privileged caller than the gate would allow.

**Type check runs after, not before, dynamic instantiation:** A handler builds a class name from request input and immediately hands it to a dynamic instantiation call (`new $class(...)` or a `$class::factoryMethod(...)` call), only inspecting the resulting object's type (`instanceof`) *after* construction — reject-on-mismatch happens too late if the base class's `__construct()` has a side effect (a DB `INSERT`, a file write) when no ID/record is supplied, since any request-named class in the expected namespace already ran its constructor before the type check could reject it. Use GREP_RESULTS `DYNAMIC_CLASS_FROM_REQUEST` to surface `new $var(...)` and `$var::method(...)` calls in files that also reference `ReflectionClass(` or a raw request superglobal — for each hit, read the enclosing function for whether a `is_subclass_of()`/`is_a()`/`in_array()`-against-an-allow-list/Reflection subclass check gates the call *before* it runs, and whether the target class's constructor (and any parent constructor) performs a write when instantiated with no arguments.

**For nopriv AJAX callbacks using internal routing frameworks (Slim, FastRoute, Lumen):** Use GREP_RESULTS `SLIM_FASTROUTE_ROUTER` to enumerate all registered routes. Each route handler is an independent authorization scope — framework-level auth middleware may have HTTP-method bypass conditions (e.g., nonce checked only for POST, returning `true` for all other methods), making state-changing GET routes fully unauthenticated regardless of POST nonce logic.

For option/transient writes, use GREP_RESULTS `OPTION_TRANSIENT_WRITES`: `wp_user_roles`/`default_role` writable by Subscriber → priv esc. `set_site_transient($key)` where `$key` attacker-controlled: check `update_plugins`/`update_themes`/`update_core`.

**`template_redirect` CPT access control:** Use GREP_RESULTS `TEMPLATE_REDIRECT_LOGIN_GATE` to surface `is_user_logged_in()` calls in files containing `template_redirect` hooks. For each hit: (1) determine whether `current_user_can()` is also present in the same function; if absent, the gate allows any logged-in user regardless of role; (2) find the CPT this handler protects and check its `register_post_type()` arguments — `'public' => true` automatically exposes a REST API route at `/wp-json/wp/v2/<slug>/` that bypasses the `template_redirect` gate entirely; confirm `show_in_rest => false` or a REST-level `permission_callback` protects the route.

**Mass Assignment (CWE-915):** Handler copies `$_POST`/`$_REQUEST` wholesale into `update_option()`/`add_option()` via `array_merge()`. `unset($from_data['nonce'])` does NOT prevent — remaining keys attacker-controlled. Use GREP_RESULTS `MASS_ASSIGNMENT`. **Impact escalation:** Option containing role/capability arrays → `update_option_<name>` hook calls `add_cap()` for listed roles → priv esc. Use GREP_RESULTS `OPTION_UPDATE_HOOKS`.

### Arbitrary Options Update — Dedicated Analysis

`update_option()`, `add_option()`, and `delete_option()` have **NO built-in capability checks** — authorization is entirely the caller's responsibility. Any code path where user-controlled input reaches these functions without `current_user_can('manage_options')` is a potential Arbitrary Options Update vulnerability.

**Canonical exploitation chain:** Attacker writes `users_can_register` = `1` + `default_role` = `administrator` → registers new account at `/wp-login.php?action=register` → new account is administrator → full site takeover. Alternative impacts: overwrite `siteurl`/`home` to redirect all traffic; overwrite `active_plugins` to deactivate security plugins; overwrite `template`/`stylesheet` to force a malicious theme; overwrite `wp_user_roles` for direct capability manipulation.

**Critical WordPress options (attacker target list):**

| Option name | Impact when overwritten |
|---|---|
| `users_can_register` | Enables open registration (default: off) |
| `default_role` | Sets role for new registrations (default: subscriber) |
| `siteurl` / `home` | Redirects all site traffic to attacker domain |
| `admin_email` | Receives password reset emails, admin notices |
| `active_plugins` | Deactivate security plugins, activate malicious ones |
| `template` / `stylesheet` | Forces loading of attacker-controlled theme |
| `wp_user_roles` | Direct role/capability modification |
| `blogname` / `blogdescription` | Stored XSS if unescaped in frontend |

**Entry point patterns (ordered by risk):**

1. **Unauthenticated AJAX/admin_post option write (CRITICAL):** Use GREP_RESULTS `NOPRIV_OPTION_WRITES` and `ADMIN_INIT_USERINPUT_OPTION_WRITE`. For each hit: trace from hook registration to callback body → confirm update_option/add_option/delete_option call → check for `current_user_can()` → if absent, CONFIRMED. This is the #1 CVE pattern.

2. **Settings import/export without auth (HIGH):** Use GREP_RESULTS `SETTINGS_IMPORT_OPTION_WRITE`. Pattern: function accepts JSON/XML file upload or request body → `json_decode`/`simplexml_load` → foreach → `update_option` per key. Check: is the import endpoint gated by `current_user_can('manage_options')`? Is there a nonce? Does the import function validate option names against an allowlist?

3. **foreach loop over user input → update_option (HIGH):** Use GREP_RESULTS `FOREACH_POST_TO_OPTION_WRITE`. When `update_option` is called inside a loop iterating over user-supplied keys, the attacker controls WHICH options are written — functionally equivalent to user-controlled option key but spread across multiple calls.

4. **admin_init handler option write (default Unauthenticated, CRITICAL):** Use GREP_RESULTS `ADMIN_INIT_STATE_CHANGES` + `ADMIN_INIT_SUPERGLOBAL_READS`. Developers commonly believe `admin_init` = admin-only, or at worst = requires login — it is neither: `/wp-admin/admin-ajax.php` fires `do_action('admin_init')` before checking `is_user_logged_in()`, so a fully unauthenticated visitor reaches it via `admin-ajax.php?action=<any>` unless the handler's own registration is gated behind `admin_menu` (see Tier 4 Layer 4 above). Do not default this pattern's floor to Subscriber.

5. **delete_option + add_option bypass (HIGH):** Use GREP_RESULTS `DELETE_OPTION_ADD_OPTION_PAIR`. Some plugins avoid `update_option()` and instead call `delete_option()` then `add_option()` to bypass `update_option_{$option}` hooks or set the autoload flag. The same vulnerability applies — if the option name or value is user-controlled, the attacker can write to critical options.

6. **URI-based / is_admin() capability check bypass:** Some plugins check `strpos($_SERVER['REQUEST_URI'], '/wp-admin/')` or `is_admin()` as an authorization gate for option writes. These are NOT capability checks — `is_admin()` returns `true` for any request to a `/wp-admin/` URL regardless of user role, and `REQUEST_URI` is fully attacker-controlled. Use GREP_RESULTS `BROKEN_AUTH_LOGIC` to surface `is_admin()` misuse and cross-reference with option-write grep hits.

7. **Critical option value write (any auth level):** Use GREP_RESULTS `CRITICAL_OPTION_VALUE_WRITE`. Direct writes to security-sensitive option names (`users_can_register`, `default_role`, `siteurl`, etc.) with non-constant values. Even if properly capability-gated, verify the value is sanitized and the option name cannot be influenced.

- `user-controlled-option-key` — user input → option KEY (CRITICAL)
- `wp-ajax-nopriv-option-write` — nopriv handler + option write + no auth (CRITICAL)
- `rest-body-to-update-option` — REST body → option value (HIGH)
- `post-mass-assign-to-option` — bulk POST → option value (HIGH)
- `settings-import-to-option-write` — JSON decode → option write (HIGH)
- `foreach-user-input-to-update-option` — foreach over user input → update_option (HIGH)
- `delete-option-add-option-bypass` — delete+add pair with variable key (HIGH)
- `admin-init-no-auth-option-write` — admin_init + option write + no auth (MEDIUM)

### Arbitrary Content Modification — Dedicated Analysis

`wp_update_post()`, `wp_insert_post()`, `wp_publish_post()`, `wp_insert_comment()`, `wp_update_comment()`, `wp_new_comment()`, `wp_set_object_terms()`, `set_post_thumbnail()`, and `delete_post_thumbnail()` have **NO built-in capability checks** — authorization is entirely the caller's responsibility. Direct `$wpdb->insert()`/`$wpdb->update()` on `wp_postmeta` bypass `is_protected_meta()` which would normally block writes to `_`-prefixed meta keys by non-admin users. Any code path where user-controlled input reaches these functions without appropriate `current_user_can()` checks is a potential Arbitrary Content Modification vulnerability.

**Canonical exploitation chains:**
- **Defacement/SEO poisoning:** Attacker modifies `post_title`/`post_content` of ANY post via `wp_update_post()` with user-supplied post ID — site defacement, watering-hole injection, SEO spam.
- **Protected meta injection:** `$wpdb->insert()` on `wp_postmeta` bypasses `is_protected_meta()` — attacker injects `_wp_page_template`, `_wp_attached_file`, `_edit_lock`, or other `_`-prefixed meta keys on duplicated/cloned posts.
- **Post status elevation:** `wp_insert_post_data` filter modifies `post_status` from `draft` to `publish` without checking `publish_posts` — Contributors bypass editorial workflow.
- **Arbitrary comment creation:** `wp_insert_comment()`/`wp_new_comment()` on arbitrary posts without `edit_post` capability check — content injection on any post. `wp_insert_comment()` runs no moderation pipeline at all (no Akismet, no blacklist, unlike `wp_new_comment()`); if its `$args` array omits the `comment_approved` key, WP Core's own default auto-approves the comment immediately (`wp-includes/comment.php`: `$comment_approved = ! isset($data['comment_approved']) ? 1 : $data['comment_approved']`), making injected content publicly visible with zero admin review. A `check_ajax_referer()`/`wp_verify_nonce()` call alone does not neutralize this — see CANON:nonce-verification for when a nonce carries zero authorization value.

**Entry point patterns (ordered by risk):**

| # | Pattern | Hook Type | Auth Floor | Write Sinks | Grep Section |
|---|---------|-----------|------------|-------------|--------------|
| 1 | Unauthenticated AJAX/admin_post content write | `wp_ajax_nopriv_`, `admin_post_nopriv_` | Unauthenticated | `wp_update_post()`, `wp_insert_post()` | `NOPRIV_CONTENT_WRITES` |

**Detection methodology:**

For each `NOPRIV_CONTENT_WRITES` hit: (1) trace from hook registration to callback body; (2) confirm `wp_update_post`/`wp_insert_post` call; (3) check for `current_user_can()` before the write — if absent, CONFIRMED; (4) check whether post ID originates from user input (`$_POST`, `$_GET`, `$_REQUEST`, `->get_param()`) — if yes, also IDOR (CWE-639); (5) if capability check IS present, verify per-resource `current_user_can('edit_post', $id)` not class-level `current_user_can('edit_posts')`.

For each `WPDB_DIRECT_POST_TABLE_WRITES` hit: (1) trace the data source; (2) check for capability checks; (3) for `$wpdb->insert` on postmeta: check whether `meta_key` is user-controlled — `is_protected_meta()` is NOT called by `$wpdb->insert()` (only by `add_post_meta()`), so `_`-prefixed keys can be injected; (4) cross-reference with import/duplicate/clone functionality.

For each `WP_INSERT_POST_DATA_FILTER` hit: (1) read the filter callback body; (2) check whether it modifies `post_status`, `post_author`, `post_type`, or `post_content`; (3) if it modifies `post_status`: verify `current_user_can('publish_posts')` or equivalent before the modification; (4) a filter that elevates `post_status` from `draft` to `publish` without checking `publish_posts` allows Contributors to bypass editorial workflow.

For each `KSES_REMOVAL_CONTENT_WRITE` hit: (1) determine who triggers this code path; (2) if reachable by users without `unfiltered_html` (Contributors, Authors), `kses_remove_filters()` before `wp_insert_post()`/`wp_update_post()` bypasses all KSES content sanitization — full HTML injection including `<script>`.

- `wp-ajax-nopriv-content-write` — nopriv handler + content write + no auth (CRITICAL)

- `wp-insert-post-data-filter-status-elevation` — filter modifying post_status without cap check (MEDIUM)
- `nopriv-comment-write-no-auth` — nopriv handler + comment write + no auth (MEDIUM)

### Self-service account-state escalation (CWE-639) — Dedicated Analysis

User-controlled input written to a meta/option KEY that governs account state — membership/plan/tier/subscription, `account_type`/`user_type`, `email_verified`/`is_verified`, `is_approved`/`is_active`/`activated`, access/user level — lets a low-privilege user self-assign a privileged state (upgrade plan, mark own email verified, approve/activate own account). This is Authorization Bypass Through User-Controlled Key (CWE-639), a privilege/verification escalation. Use GREP_RESULTS `ACCOUNT_STATE_FIELD_FROM_INPUT`; Semgrep lead `claude.php.wordpress.access-control.user-input-to-account-state-meta` (heuristic).

Detection: for each `update_user_meta($uid, $key, <request value>)` / `update_option($key, <request value>)` where `$key` names an account-state field: (1) confirm the value is attacker-chosen (from `$_GET`/`$_POST`/`$_REQUEST`/`php://input`), not derived from a server-validated source or constrained by an allowlist — `intval()`/`absint()` do NOT neutralize a logic-value choice (the attacker still picks the tier/level/flag); (2) confirm no `current_user_can()` gate authorizes the transition for the requesting user; (3) confirm the target state is server-derived, not client-supplied, and (for state machines) the SOURCE state is verified first. The `wp_capabilities` key and `set_role()`/`add_cap()` sinks are mass-assignment / role-write findings (see above) — this covers the non-capability account-state fields. Real-world: unauthenticated booking/appointment status transitions. The workflow-step / sequential-state and one-time-replay facets that reach an auth sink are analyzed in Group AB (subsection E.11).

### Plugin / Theme Installation or Activation — Dedicated Analysis

`activate_plugin()`, `activate_plugins()`, `Plugin_Upgrader::install()`, `Theme_Upgrader::install()`, `switch_theme()`, and the manual `download_url()` + `unzip_file($pkg, WP_PLUGIN_DIR)` install primitive have **NO built-in capability check** — authorization is entirely the caller's responsibility. A path reaching any of these from an unauthenticated or low-privilege entry point without `current_user_can('install_plugins' | 'activate_plugins' | 'install_themes' | 'switch_themes')` is the #1 route to full RCE/site takeover: installing an attacker-supplied plugin ZIP yields code execution. **Core's own AJAX handlers are the correct-gating baseline** — `wp_ajax_install_plugin`/`install_theme`/`update_plugin`/`delete_plugin` each call `check_ajax_referer('updates')` AND `current_user_can('install_plugins'|...)` (ajax-actions.php). A plugin re-implementing install/activate without that gate is the finding.

**Canonical exploitation chains:**
- **Unauth/permissive-REST → arbitrary install → RCE:** a `register_rest_route()` with `permission_callback => '__return_true'`, or a `wp_ajax_nopriv_`/`admin_post_nopriv_` handler, runs `Plugin_Upgrader->install($attacker_url)` or `download_url()`+`unzip_file($zip, WP_PLUGIN_DIR)` with no cap check → attacker installs a webshell plugin.
- **Subscriber via exposed nonce (nonce-theater):** handler verifies a nonce but has **no** `current_user_can()`; the nonce is rendered into admin UI reachable by Subscribers → Subscriber installs from an attacker URL. A custom nonce-hash substituted for the cap check is still no authorization.
- **CSRF → admin-triggered install:** capability-gated install/activate with **no nonce** → forged request rides a logged-in admin's session.
- **Activation-only / security disable:** Subscriber+ reaches `activate_plugins`/`switch_theme` with an attacker-chosen target → activate a dormant malicious plugin / force a malicious theme; or `deactivate_plugins` a security plugin.

**Target-sink table:**

## Tier 4B — CSRF on State-Changing Admin GET Endpoints (CVSS 4.3–6.5)

**In scope when forged request has real CIA impact.** WordPress auth cookies default SameSite=Lax.
- **GET CSRF: NOT prevented** — top-level GET navigation sends SameSite=Lax cookies. State-changing GET endpoints fully exploitable.
- **POST CSRF: Browser-mitigated** — cross-site POST does NOT send SameSite=Lax cookies (Chrome 80+, Firefox 79+).

`current_user_can()` without nonce = CSRF confirmed (verifies capability, not request origin).

**Ambient-hook registration as the implicit capability gate:** a callback already registered unconditionally on an always-firing hook (`admin_notices`, `all_admin_notices`, `admin_init`) whose own body branches on `$_REQUEST`/`$_GET`/`$_POST` to perform a state change has no inline `current_user_can()` to find — the capability check (if any) happened earlier, at registration time (→ core SKILL.md item 22). Treat a capability-gated registration as equivalent to an inline `current_user_can()` for this rule: if the callback body itself verifies no nonce before the state change, CSRF is still confirmed, with the ambient hook (not a specific admin page) as the delivery surface.

Detection: (1) grep for `$_GET['view'|'action'|'task'|'do']` in admin page callbacks; (2) read conditional branch; (3) check `check_admin_referer()`/`wp_verify_nonce()` before `$wpdb->delete/update/insert()` or `wp_redirect()`; (4) confirm `current_user_can()` present (admin victim needed) but no nonce. Use GREP_RESULTS `CSRF_STATE_CHANGES`.

**Token-listener variant (page-load OAuth callback, not a dispatched GET action):** a function reads a credential/token value directly from `$_GET` (e.g. `access_token`, `oauth_token`) into a token-shaped array key, while the actual `update_option()`/`add_option()` persistence happens in a *different* function that consumes its return value — common in "connect your account" listeners invoked on ordinary admin page load rather than a dedicated AJAX action. There is no sink call next to the missing nonce check to spot; verify nonce presence inside the token-reading function itself. Use GREP_RESULTS `GET_ACCESS_TOKEN_PARAM` / `claude.php.wordpress.access-control.get-request-token-listener-no-nonce`.

**File-write variant (attachment/media replace, direct upload handlers):** the same `current_user_can()`-without-nonce rule applies to AJAX/admin-post handlers that overwrite an existing file — `move_uploaded_file()`/`copy()`/`rename()`/`file_put_contents()`/`wp_handle_upload()`/an uploader object constructed directly from `$_FILES` — reachable only via `wp_ajax_<action>` (not `_nopriv`, so a logged-in victim holding the resource capability is still required). The canonical shape is a handler where `current_user_can('edit_post', $id)` gates the write but no `check_ajax_referer()`/`wp_verify_nonce()` exists anywhere in it. Use GREP_RESULTS `AJAX_AUTHENTICATED_FILE_WRITE_SIGNAL` / `claude.php.wordpress.csrf.file-write-capability-only-no-nonce`.

**REST routes are the exception to the rule above — verify before applying it to `register_rest_route()` callbacks.** WordPress Core's `rest_cookie_check_errors()` (`wp-includes/rest-api.php`) demotes any cookie-authenticated REST request lacking a valid `wp_rest` nonce to `uid 0` *before* the route's `permission_callback` runs — it does not reject the request outright (only a present-but-*invalid* nonce is hard-rejected). Consequence: a CSRF-forged cross-site request cannot supply the victim's nonce, so it is demoted to anonymous, and any `permission_callback` performing a genuine `current_user_can()`/`is_user_logged_in()` check correctly rejects it. Therefore a capability-gated REST route missing its own explicit nonce check is **NOT automatically CSRF-exploitable** — this Core-level backstop applies only to `register_rest_route()` endpoints; the classic admin-form/AJAX/admin-post rule above (`current_user_can()` without nonce = CSRF confirmed) has no such backstop and still applies unchanged to those non-REST endpoints.

## Tier 11 — IDOR (CVSS 4.3–7.5)

**ID-space confidence gate:** an attacker-controlled resource ID with no ownership check is not automatically IDOR-confirmed — the ID's namespace matters. Small sequential per-merchant/per-site integers (WooCommerce `order_id`, WP `post_id`/`user_id`) are trivially enumerable and clear the >90% confidence bar on the missing-check alone; a large, platform-wide, or externally-allocated identifier (e.g. a payment-processor transaction/notification ID) requires either an independent disclosure primitive for a valid ID or a demonstrated high-success-likelihood guessing method before it clears confidence — do not equate "attacker-controlled ID + no ownership check" with confirmed IDOR when the ID space itself is a practical barrier (→ global CLAUDE.md's brute-force exploitability carve-out).

**Shared/site-wide resource gate:** a missing per-record ownership check is not IDOR when the resource was designed as a shared/site-wide record rather than a per-user-owned one (e.g. a global activity/audit log every holder of the gating capability is expected to see and manage in full) — there is no victim whose data boundary is crossed. Verify whether the plugin's own data model scopes the resource to an individual owner (a `user_id`/`author_id`/`customer_id` column checked anywhere else against the record) before treating a missing per-record check as Missing Authorization/IDOR.

Use GREP_RESULTS `TIER11_IDOR`, `IDOR_OWNERSHIP_CHECKS`, `REST_IDOR_USER_ID`, `REST_IDOR_RESOURCE_ID` (or `AUDIT_DIR/grep/group-ac-results.md` in file-based mode).

**REST_IDOR_USER_ID:** Check whether function overwrites `get_current_user_id()` with param → identity substitution IDOR.
**REST_IDOR_RESOURCE_ID:** For DELETE/PUT handlers, check symmetric ownership: handler fetches resource, compares ownership field against `get_current_user_id()` BEFORE write/delete.

**REST_BODY_PARAM_POST_ID:** REST callbacks reading JSON body params may extract a post/object ID that is passed to `get_post()` without a per-resource auth check. Use `REST_BODY_PARAM_POST_ID` grep results. For each hit: (1) trace whether any parameter from the body is used as a post/resource ID; (2) verify that `current_user_can('read_post', $id)` is called before the post content is accessed — `current_user_can('edit_posts')` in the `permission_callback` is a class-level gate and does NOT authorize reading private or draft posts authored by others; (3) this pattern also applies when content is relayed to an external service (AI API, translation, OCR) — indirect disclosure via a third-party service constitutes IDOR (C:L) even when the raw content is not returned to the caller.

**Symmetric ownership check:** Developers scope list endpoints to "your records" but forget scoping on write/delete. Read scoped + write unscoped = IDOR regardless of capability check. Methodology: (1) find list endpoint scoping; (2) find write/delete for same resource; (3) `get_current_user_id()` compared against record ownership field BEFORE write?
   - **Custom table WHERE clause audit:** For every `$wpdb->update`/`$wpdb->delete`/`$wpdb->query` on a custom table that has a user-ownership column (e.g., `user_id`, `blog_user_id`, `created_by`), verify the WHERE clause includes `AND [ownership_col] = get_current_user_id()` — capability + nonce checks authorize the action class but not the specific record.
   - **Custom (non-WP-native) auth pipelines use a custom identity-object comparator, not `get_current_user_id()`.** A plugin implementing its own token/pseudo-role auth layer (a mobile-app API, a custom REST-like scheme) typically resolves the caller into `$this-><identity>` (e.g. `$this->staff`, `$this->member`) and compares `$this-><identity>->getId()` against a record's owner field instead — see `IDOR_OWNERSHIP_CHECKS` grep results for this comparator shape. Confirming the auth layer itself is unforgeable (an authentication question) does not close this Tier 11 analysis — every sibling record-scoped method in the same handler class still needs its own ownership-check verification; one correctly-scoped method (e.g. a delete handler) does not imply its siblings (read/create/update handlers) enforce the same check.

**Illusory auth check:** Compares current user ID against user-*supplied* parameter, not fetched record's owner. Attacker sends own ID to pass check, submits victim's record ID. Use GREP_RESULTS `ILLUSORY_OWNERSHIP`.

**Nonce scoped to type, not object:** Nonce action contains field/action type but NOT object ID. One valid nonce works for ALL objects. Detection: check whether nonce action string includes the accepted `object_id`/`post_id`.

**Identity substitution IDOR (REST):** Access function is correct but user identity passed to it is attacker-supplied. `permission_callback` assigns `get_current_user_id()` then overwrites with `$request->get_param('user_id')`. Check evaluates victim — attacker gets in. Detection: grep `get_param.*user_id` in permission callbacks; check for assignment overwrite.

**Type-discriminated permission gate — incomplete arm coverage (REST):** A shared `permission_callback` resolves a resource ID via a per-type `match`/`switch` on a `context`/discriminator field, checking ownership only for the type values it explicitly handles (e.g. `'post'`/`'comment'`) while a `default` arm returns `null` for every other legitimate type value (e.g. `'user'`/`'term'`) — the caller then enforces its ownership check only when the resolved ID is truthy, so any unhandled type silently bypasses authorization. Detection: read every arm of the discriminator match/switch and confirm each type the endpoint actually accepts has a corresponding check; use GREP_RESULTS `REST_PERMISSION_TYPE_DISCRIMINATOR_NULL_DEFAULT` / Semgrep `rest-permission-callback-type-discriminator-fallthrough`.

**Capability check on the wrong subject (CWE-639):** A request-controlled id resolves a *target* user object, and the target's own capability/role method (`can_*`/`is_*`/`has_*`) gates access instead of the caller's — typically `if ( ! $target->can_X() && get_current_user_id() !== $user_id ) { deny(); }`. This only denies when the target lacks the capability AND the caller isn't the target, so any caller passes whenever the *target* happens to have the capability (e.g. the id points at an instructor/admin). Use GREP_RESULTS `CAPABILITY_CHECK_ON_TARGET_OBJECT`. For each hit: (1) confirm the id feeding the target lookup is request-controlled, not session-derived; (2) confirm the capability call is on the looked-up target, not on `get_current_user_id()`/`wp_get_current_user()`; (3) check whether the containing function is unreachable dead code behind an unconditional early return (a common soft-deprecation idiom) before treating it as live.

**user_id from POST/GET → per-user writes:** An authenticated AJAX handler accepting `user_id` from `$_POST` must verify `current_user_can('edit_user', $user_id)` before any per-user write — whether that write is a direct `update_user_meta($user_id, ...)` call or a static/instance method call that performs user writes internally. `check_ajax_referer()` establishes session authenticity but not per-user ownership; nonce-only handlers with POST user_id are Missing Authorization (CWE-862). Use GREP_RESULTS `USER_META_WRITES` and `TIER11_IDOR`. **Plugin wrapper functions:** helpers with `$user_id = null` default are safe only when called without explicit ID; call sites passing `$_POST['user_id']` bypass default. Trace ALL call sites, including static (`Class::method($user_id, ...)`) and instance (`$obj->method($user_id, ...)`) wrappers — the ownership check must be in the handler, not only inside the wrapper.

**Self-registerable role + ownership gap:** PR becomes effectively N.

**Cookie-based ownership proof (unauthenticated users):** Plugins using client cookie + POST-sourced key comparison for auth → both sides attacker-controlled. `$_COOKIE['key'] === $_POST['key']` → trivially bypassed when target key learned from shared URL. Detection: `$_COOKIE` reads in auth helpers; same key in public shareable URLs. Compare unauthenticated path (`$_COOKIE`) vs authenticated path (`get_user_meta(get_current_user_id())`) — asymmetry confirms flaw.

**Nopriv data retrieval without post_status gate:** Nopriv AJAX handlers that read data from custom tables keyed by a WP post ID (e.g., `CustomModel::where('table_id', $id)`, `get_post_meta($id, ...)`) without calling `get_post($id)` to verify `post_status === 'publish'` (and, separately, `post_password_required($id)`) leak draft, private, pending, trashed, or password-protected content. Check for inconsistency: parallel handlers for the same data (e.g., two rendering engines) where one validates post_status/password and the other does not — document as a lead/architectural fact regardless, since the disclosed post/page/CPT content is OOS per the Scope Gate (core SKILL.md item 8) no matter how the gap is reached; do not confirm unless the same gap also exposes user/customer PII. Use GREP_RESULTS `NOPRIV_WP_QUERY_POST_STATUS` and `NOPRIV_CUSTOM_TABLE_POST_STATUS`.


**`wp_update_post` post re-parenting IDOR:** `wp_update_post()` does not verify that the caller owns the target post. When both `'ID' => $id` and `'post_parent' => $new_parent` are set and `$id` is caller-influenced (direct `$_POST`, WooCommerce order meta written from `$_POST`, or any stored value derived from user input via `sanitize_text_field()` + `explode()`), any valid post ID can be re-parented to the attacker's resource regardless of post type — re-parenting attachments to attacker orders (C:L: file metadata disclosed), pages (A:L: permalinks break), or product variations (A:L: variation orphaned from parent product, purchase impossible). Auth gate required before call: `current_user_can('edit_post', $id)`. Use GREP_RESULTS `WP_POST_REPARENTING`; cross-reference `POST_INSERT_UPDATE` (group-c) for all `wp_update_post` call sites.

**WooCommerce order-received/order-pay/view-order IDOR via independent resolution:** `wp_head` fires before `the_content` — any callback registered there executes before WooCommerce validates the order key inside the `[woocommerce_checkout]` shortcode. Plugins (tracker pixels, conversion pixels) that call `wc_get_order()` with the order ID extracted from `query_vars['order-received']` in a `wp_head` callback and emit order data (total, currency, product IDs) without first verifying `$_GET['key']` against `$order->get_order_key()` expose all orders to unauthenticated enumeration via sequential order IDs. The query var extraction and `wc_get_order()` call may be in separate functions across an indirect call chain — check `WC_ORDER_RECEIVED_QUERY_VAR` grep results for the extraction site, then trace callers to locate `wc_get_order()`. Check: (1) grep `WC_ORDER_RECEIVED_QUERY_VAR` for any `query_vars['order-received'|'order-pay'|'view-order']` or `get_query_var('order-received'|'order-pay'|'view-order')` reads; (2) confirm the reading function or its caller is registered on a hook that fires independent of WooCommerce's own content-template key check — `wp_head` (fires before `the_content`) is the canonical example, but `wp_print_footer_scripts`/`wp_footer` are equally exploitable since they fire AFTER the content area regardless of whether the template's own key check passed or failed; only `template_redirect` (which WC uses to redirect on an invalid key before any output) is safe. **A second, independent shortcode/block callback rendered in the same `the_content` pass as WooCommerce's own key-checking shortcode is an equally valid vector even though it isn't hook-based at all** — `do_shortcode()` processes each registered tag independently, so a sibling shortcode's own `wc_get_order()` call is unaffected by a neighboring shortcode's internal key validation; (3) confirm no `get_order_key()` / `get_query_var('order-key')` / `key_is_valid()` call validates the key before order data is emitted. The `order-pay` query var resolves `shop_subscription` objects transparently when the ID is a subscription's own post ID (`WC_Subscription extends WC_Order`) — a hit on this variant can disclose a subscription's own `order_key`, not just a one-time order's totals, which is a materially higher-impact leak (the key becomes a reusable secret for any other order-key-gated write elsewhere in the same plugin — see Chain pattern "Info Disclosure → Resource-Secret-Gated Write"). `view-order` (My Account "View Order") is a structurally identical third endpoint reached via `/my-account/view-order/{id}/` rather than checkout.

**Multiple reachability triggers, inconsistent validation:** if the receipt-page gate is an OR of several trigger parameters, verify each branch's key-check strength separately — a compatibility branch for a different payment integration's return-URL convention may require no key at all.

**Account takeover via wp_update_user / wp_set_password IDOR (CVSS 8.1–9.8):** Highest-impact IDOR subtype. Attacker supplies victim's user_id to a handler that calls `wp_update_user()` (changes email/password/role) or `wp_set_password()` (resets password directly). Neither WP Core function performs internal authorization — the caller must verify `current_user_can('edit_user', $user_id)` before invocation. Use GREP_RESULTS `IDOR_ACCOUNT_TAKEOVER_SINKS`, `USER_META_WRITES`, `TOKEN_AUTH_FLOWS`. Detection: (1) For each `wp_update_user()` hit: trace the `'ID'` key in the argument array — if it originates from `$_POST`, `$_GET`, `$_REQUEST`, `$request->get_param()`, or any user-controlled source, confirm no `current_user_can('edit_user', $user_id)` call gates the path. (2) For each `wp_set_password()` hit: trace the second argument (`$user_id`). Additionally check whether the handler uses a cryptographically verified reset token (`check_password_reset_key()`) — custom reset flows that skip this are vulnerable. (3) For `wp_set_auth_cookie($user_id)`: if `$user_id` is attacker-controlled and no cryptographic identity verification precedes the call, this is instant account takeover (CVSS 9.8). Verify the identity is established via `wp_signon()` return value or a verified token, not from a POST parameter. (4) Check registration context: `wp_ajax_nopriv_` (unauth) → CVSS 9.8; `wp_ajax_` (Subscriber+) → CVSS 8.1.
   - **Config-resolved target, not just a raw request ID** (→ core SKILL.md FN Prevention #10): the "user-controlled source" test above also covers a target ID resolved via an admin-configured RELATIONSHIP — e.g. a front-end form action set to "update the current post's author" or "update this one fixed chosen user" — rather than a literal `$_POST`/`$_GET` read at the `wp_update_user()`/`wp_set_auth_cookie()` call site. If the resolved ID is never compared against `get_current_user_id()`, the requester can still reach an account other than their own (by choosing which context/page to submit from, or simply because the fixed configured target isn't them), even though no raw ID parameter appears at the sink itself.
**AJAX/REST post_meta write IDOR (CVSS 4.3–6.5):** Handlers accepting a post_id from user input and calling `update_post_meta($post_id, ...)`, `delete_post_meta($post_id, ...)`, or `add_post_meta($post_id, ...)` without `current_user_can('edit_post', $post_id)`. The `check_ajax_referer()` nonce verifies intent, not per-resource ownership. Use GREP_RESULTS `IDOR_POST_META_WRITES`, cross-reference `TIER4_CAPABILITY_CHECKS`. Detection: (1) For each `update_post_meta`/`delete_post_meta`/`add_post_meta` hit: trace first argument back to user input source. (2) Check for `current_user_can('edit_post', $post_id)` (singular + ID) anywhere before the call in the same execution path — `current_user_can('edit_posts')` (plural, no ID) is a class-level gate and does NOT authorize specific posts. (3) Impact depends on what metadata is being written: plugin settings metadata (low impact) vs `_wp_attached_file` / `_thumbnail_id` / pricing fields (higher impact).
**Nonce-only multi-item save loop, resource index from dynamic field name (CVSS 6.5–8.8, often Stored XSS):** A save handler verifies only a nonce (`wp_verify_nonce()`/`check_admin_referer()`), then iterates `$_POST`/`$_REQUEST`, extracting a resource index from each dynamic field-name key (e.g. `$index = (int) str_replace($prefix, '', $name);` behind `strpos($name, $prefix) === 0`), and writes the submitted value into a collection keyed by that index — a collection persisted via `update_option()`/`update_post_meta()`/equivalent — with no per-resource capability/ownership re-check for the SPECIFIC index. A nonce proves CSRF intent only; it does not prove the submitter is authorized for the resource the forged index selects. Common in plugins offering delegated per-page/per-item editing access (repeater fields, custom-field builders, multi-tab settings with role-scoped tabs): a user legitimately granted access to ONE item/page can forge indices belonging to OTHER items/pages they were never granted, hijacking fields tied to a different, possibly higher-privileged resource — frequently escalating to Stored XSS when the hijacked field's content (e.g. a raw code/HTML field) is rendered elsewhere without re-escaping. Use GREP_RESULTS `DYNAMIC_FIELD_INDEX_NO_PER_ITEM_AUTHZ`. Detection: (1) confirm the extracted index truly selects among multiple independently-scoped resources (not just a single fixed-resource option); (2) search the WHOLE function for ANY per-resource authorization call gating the write for that specific index — helper names vary widely (`can_access_*`, `user_can_*`, a role-hierarchy comparison), so a missing literal `current_user_can()` call is not proof by itself, but a genuine absence of ANY per-index check is; (3) confirm each index maps to an independently-configurable owner/page/role before treating this as cross-resource IDOR rather than a single-resource bug.
**Post/attachment deletion IDOR (CVSS 5.3–8.1):** Handlers calling `wp_delete_post($id)` or `wp_delete_attachment($id, true)` where `$id` is user-supplied, without `current_user_can('delete_post', $id)`. `wp_delete_attachment($id, true)` permanently removes the DB record AND the physical file from `wp-content/uploads/` — irreversible. `current_user_can('delete_posts')` (plural) checks class-level permission, not ownership. Use GREP_RESULTS `IDOR_POST_DELETE`, cross-reference `TIER2_FILE_DELETE` and `TIER2_CONTENT_DELETE` (group-a). Also check `TIER2_CONTENT_DELETE` for comment, term, user, and metadata deletion sinks that may have IDOR patterns — `wp_delete_comment($id)`, `wp_delete_term($id, $taxonomy)`, `wp_delete_user($id)`, `delete_user_meta($id, $key)` all accept user-supplied IDs and perform no internal ownership verification.
   - **"User-supplied" includes IDs resolved via a plugin-internal template-tag/merge-tag engine** (→ core SKILL.md FN Prevention #10): a delete sink fed by `$row['file']`/similar resolved through a `{field:key}`/`{tag:key}`-style resolver that ultimately reads a staged request cache is exactly as attacker-controlled as a direct `$_POST['id']` read — the ID doesn't need to appear as a literal superglobal access next to the deletion call to be in scope.
**Payment/order IDOR (CVSS 5.3–7.5, often unauthenticated):** Payment gateway callbacks, IPN handlers, and webhook endpoints calling `wc_get_order($order_id)` where `$order_id` is attacker-supplied. Payment callbacks are frequently `wp_ajax_nopriv_` or standalone PHP endpoints with no WordPress auth. Use GREP_RESULTS `IDOR_WC_ORDER_ACCESS`, `TIER11_IDOR` (wc_get_order.*query_vars). Detection: (1) Identify all `wc_get_order()` calls where the order ID comes from user input (POST/GET parameter, webhook body, URL path component). (2) Check for order key validation: `$order->get_order_key()` compared against a request parameter via `hash_equals()`. WooCommerce order IDs are sequential integers — without key validation, any integer enumerates orders. (3) Payment callback specifics: look for `$_POST['order_id']` or JSON body extraction in handlers registered for payment provider webhooks — these are often unprotected by nonce. (4) Impact: order total, currency, customer email, product list, billing address disclosed. In write cases (mark order paid, update status), financial fraud is possible.
   - **Order-key possession ≠ account ownership for durable-state writes:** `key_is_valid()`/`hash_equals()` against an order key proves possession of a per-order bearer secret — sufficient authorization for a one-time action scoped to that same order (view/pay-for-order), but NOT for a write that persists beyond the transaction and affects future behavior (e.g., reassigning a subscription's stored payment method/gateway for all upcoming renewals). For any order-key-gated handler whose sink is a "change/save/update payment method" or "update recurring billing" call, verify the function ALSO checks `is_user_logged_in()`/`current_user_can()`/`get_current_user_id()` against the resource's owner — its absence here, especially when a structurally similar sibling branch in the same class/dispatcher DOES include that binding, is confirmed Missing Authorization regardless of the key check's own correctness.
   - **Optional secondary-identifier check bypassed by omission:** a conditional re-binding check written as `if ($secondary_param) { $id = resolve_via_secondary($secondary_param); }` with no `else`/rejection branch is not equivalent to requiring the secondary identifier — omitting the parameter entirely (rather than supplying an invalid value) skips the check silently and falls through to whatever untrusted raw ID was already assigned earlier in the function. Verify the check fires unconditionally, or that the omission path is itself rejected, before treating an optional-if-present re-binding call as a real ownership gate.
**Attachment/file access IDOR (CVSS 4.3–6.5):** Handlers calling `get_attached_file($id)`, `wp_get_attachment_url($id)`, or `wp_get_attachment_image_src($id)` where `$id` is user-supplied, without `current_user_can('read_post', $id)` (attachments are post_type 'attachment' — standard post capabilities apply). Use GREP_RESULTS `IDOR_ATTACHMENT_FILE_ACCESS`. Detection: trace ID argument to user input; verify per-resource check. Private attachments (uploaded to private/draft posts, or explicitly set private) should not be accessible to unauthorized users. The file path itself may contain PII (original filename from uploader's computer).
**Shortcode attribute IDOR:** Shortcode callbacks extract resource IDs from `$atts` (e.g., `$atts['id']`, `$atts['post_id']`, `$atts['user_id']`). Shortcode attributes are fully user-controlled when the shortcode appears in user-editable content (Contributor+ posts, bbPress forums, BuddyPress activity). Even on admin-authored pages, some themes allow URL parameters to override shortcode attributes. Use GREP_RESULTS `IDOR_SHORTCODE_ATTRIBUTE_ID`, cross-reference `SHORTCODES` (surface). Detection: for each shortcode that accepts an ID attribute, trace whether the ID reaches a write/delete/sensitive-read WP API call without per-resource auth. Shortcodes registered via `add_shortcode()` execute in the `the_content` filter context with the page author's ambient permissions — there is no WordPress-enforced auth gate on attribute values. Cross-handler consistency check: when the same CPT resource is also served by AJAX or REST handlers, compare post_status enforcement — an AJAX handler that includes `AND posts.post_status = 'publish'` in its SQL or calls `get_post_status()` as a gate while the shortcode calls `get_post_meta($atts['id'], ...)` without an equivalent check is a confirmed IDOR; cross-reference `IDOR_SHORTCODE_ATTRIBUTE_ID` against `NOPRIV_CUSTOM_TABLE_POST_STATUS` results to surface this inconsistency.

**Post content disclosure IDOR — SCOPE GATE APPLIES:** AJAX/REST handlers calling `get_post($id)` and accessing `->post_content`, `->post_excerpt`, or `->post_title` without `current_user_can('read_post', $id)` leak draft, private, pending, trashed, or password-protected content — a real access-control gap worth documenting as a lead/architectural fact. But the disclosed resource is post/page/CPT content, which is OOS per the Scope Gate (core SKILL.md item 8) regardless of the missing-check mechanism (status check vs. access-control/password bypass) — do NOT confirm as IDOR. Indirect disclosure (sending content to an external API without returning it to the caller) is the same test: still OOS if the disclosed data is post/page/CPT content, in-scope only if it is user/customer PII. Use GREP_RESULTS `IDOR_POST_READ_NO_AUTH`, cross-reference `REST_BODY_PARAM_POST_ID`. Detection: trace ID to user input; check for `current_user_can('read_post', $id)` or `post_status === 'publish'` gate before content access. `get_post()` returns posts of ANY status — there is no internal status filtering.

**Comments are NOT covered by the post-content Scope Gate:** The OOS carve-out above applies only to the post/page/CPT object's own fields (`post_content`/`post_excerpt`/`post_title`/slug/metadata). Comments (`wp_comments` rows) attached to a non-public or password-protected post are a distinct resource type — unauthorized read (`get_comments()` without `post_status`/`post_password_required()` gating) or write (`wp_new_comment()`/`wp_insert_comment()` without the equivalent eligibility checks) is ordinary in-scope Missing Authorization / Information Disclosure, not the content carve-out. Do not dismiss a comment read/write finding by analogy to the post-content OOS rule.

## Group AC — FP Verification Rules

These rules supplement the universal FP rules in the shared core SKILL.md Phase 4.

8. **REST endpoint forwarding query params to WP_Query:** Verify override order — safety-critical keys (`post_status`, `has_password`) set AFTER user args = cannot be bypassed. Same check applies to AJAX handlers passing user input as the first `wp_parse_args()` argument — → see core SKILL.md FN Prevention #3.

10. **Semgrep "missing permission_callback":** Check `array_merge()` with per-method callback arrays — Semgrep can't trace multi-level merges.

15. **Transient-based token auth:** `===` comparison = FP. `==` = TP (CWE-697): `null == false` → true when transient absent. Also check for unauthenticated transient delete/regenerate endpoints.

24. **Dispatcher global cap ≠ per-item auth; user-controlled meta key** — Global check = minimum privilege. Verify each write branch enforces per-item ownership. For `add_user_meta()`/`update_user_meta()`: check `$unique` arg, whether `$user_id` is bound to `get_current_user_id()`; `$unique=true` + existing key = silent `false`.
   - Export and file-download branches require the same per-resource ownership check as write branches — disclosing any resource's configuration by attacker-supplied ID is IDOR (C:L, CVSS 4.3+) even with no write.
   - `wp_update_post(['ID' => $id, 'post_parent' => ...])` is an under-recognized IDOR sink — WordPress does not verify caller ownership of `$id`; any caller-influenced value re-parents the target post regardless of capability level.
   - `wp_delete_attachment($id, true)` is constrained to Media Library records (`wp_posts` where `post_type='attachment'`); it cannot delete `wp-config.php` or arbitrary filesystem paths; the "Arbitrary File Delete → Install Wizard → Admin" chain is not applicable — report this finding at its true impact (irreversible Media Library deletion, I:H).
   - When the VALUE argument to `update_user_meta()`/`add_user_meta()` is a string literal (hardcoded constant, not a variable), the stored value cannot carry an XSS payload regardless of what the KEY argument contains — taint in the KEY does not propagate to the stored VALUE; flag only when a user-influenced variable reaches the VALUE position.
   - **Single-tenant data model exception:** when no object type in the plugin's data model (buttons, integrations, connections, etc.) has a per-user/per-tenant ownership column — verified against the schema/model, not just the handler code — and every handler reaching those objects already requires the same site-wide capability, classic per-user IDOR does not apply: there is no other lower-privileged user's object the caller could be confused with. Confirm the absence of any ownership column before dismissing a GET-by-ID read/write on this basis.
   - **Self-scoped query, no attacker-writable scoping data:** a handler missing `current_user_can()`/role check is not Missing Authorization when its own query/filter logic already restricts results to the caller (e.g. `in_array(get_current_user_id(), $ownership_array)`) AND no lower-privileged write path can influence that scoping array/column — verify both conditions independently before dismissing, since either one alone is insufficient.
   - **Compound/multi-factor identity proof — verify every participating function independently.** When a plugin identifies an unauthenticated/guest requester's target record via two or more independently-supplied values that must jointly resolve to it (e.g. an email + a record-reference string), confirming that ONE resolver function in the chain correctly binds both factors does not verify a SIBLING function implementing a different piece of the same proof — independently trace each participating function's handling of its own attacker-controlled input, especially its behavior on empty/malformed input (does it fail closed or silently drop its factor and degrade to the other alone?).

26. **Post-query redaction** — Redaction targeting `$user->data->user_pass` fails when `fields` set to array (flat `stdClass`). Verify redaction matches all return shapes.

31. **ORM/model setter defaults** — `set_data($data, $role = 'admin')` called without role arg = admin-level field access. Check allowed params for public/guest roles.

32. **Meta wrapper with null default** — Safe only when called without explicit user ID. Call sites passing `$_POST['user_id']` bypass default. Trace ALL call sites.

34. **SameSite=Lax and CSRF** — Blocks cross-site POST. Does NOT block GET via top-level navigation. → See Tier 4B.

35. **REST global cap ≠ per-resource auth** — `current_user_can('edit_posts')` (plural, no ID) = role check only. DB schema with ownership column + no ownership check in handler → IDOR.
  - **CPT capability remapping:** When `register_post_type()` uses a custom `capabilities` array or non-default `capability_type`, the global `publish_posts` primitive maps to a plugin-specific admin-only cap that `wp_insert_post()` does not enforce. Verify via GREP_RESULTS `CPT_CUSTOM_CAPABILITIES`; a handler checking `current_user_can('publish_posts')` is a false auth gate for that CPT.
  - **`capability_type: 'page'` silent remapping (common):** A CPT registered with `capability_type: 'page'` and `map_meta_cap: true` silently maps `edit_posts` → `edit_others_pages` (Editor+) and `publish_posts` → `publish_pages` (Editor+); neither `wp_update_post()` nor `wp_insert_post()` enforces these remapped caps. Use GREP_RESULTS `CPT_PAGE_CAPABILITY_TYPE` to surface these CPT registrations; a handler gating `wp_update_post()` on `current_user_can('edit_posts')` (Contributor+) or `wp_insert_post()` on `current_user_can('publish_posts')` (Author+) is a false auth gate for that CPT.
  - **`get_posts()`/`WP_Query` do not enforce CPT capabilities for reads:** `get_posts()` and `new WP_Query()` execute queries without enforcing `register_post_type()` capability arrays — only the WP REST API router enforces CPT read capabilities. When a REST or AJAX handler passes a user-supplied `post_type` to `get_posts()`/`WP_Query`, verify an explicit allowlist or per-CPT `current_user_can()` check exists; use GREP_RESULTS `REST_POST_TYPE_PARAM`.
  - In WP REST controllers, `permissions_check()` is the fallback gate for all HTTP methods lacking a dedicated permission callback — when `update_item_permissions_check()` requires a higher capability than `permissions_check()`, POST and DELETE operations fall back to the weaker generic gate. Verify that `create_item_permissions_check()` and `delete_item_permissions_check()` exist and enforce the same capability level as `update_item_permissions_check()`; use REST_PERMISSION_CHECK_HAS_CAP grep section to surface the pattern.
  - `register_post_meta()` without `auth_callback` is NOT a missing-auth finding — WP Core enforces `edit_post_meta` per-object capability in `WP_REST_Meta_Fields::update_meta_value()`, limiting Contributors to their own posts. Contrast: `register_rest_field()` `update_callback` is fully developer-written and must include its own `current_user_can()` check.
  - When the meta key is `_`-prefixed and `auth_callback` is omitted, WP Core defaults `auth_callback` to `__return_false` (wp-includes/meta.php:1516), blocking REST writes for ALL non-admin users regardless of post ownership — `show_in_rest: true` makes the meta READABLE via REST but not writable by Contributors; verify the key's `_` prefix before treating a missing `sanitize_callback` as an exploitable REST write path.
  - When a read-list permission callback (`get_items_permissions_check`) is also registered as the `permission_callback` for destructive endpoints (purge, bulk delete, mass cancel), read the destructive handler independently — ownership filters applied inside the read handler are NOT automatically applied in the destructive callback. The permission check grants class-level access; scope restriction requires explicit filtering in each destructive function body.

36. **PHP session-gated AJAX handlers** — An AJAX handler lacking nonce and capability checks is not independently exploitable when its core logic reads `$_SESSION` state set exclusively by a prior capability-gated action. Verify that calling the handler with an unset/empty session key causes execution to halt before any write operation (e.g., factory returns `null` → fatal error on method call).

37. **Settings API `sanitize_callback` auth delegation** — Functions or closures passed as the `sanitize_callback` argument to `register_setting()` are invoked exclusively by the Settings API, which enforces `manage_options` (or the capability specified in the third argument) before firing any sanitize callback. Read the `register_setting()` call site rather than the callback body when evaluating missing authorization on functions included from external files.

44. **`ACCOUNT_STATE_FIELD_FROM_INPUT` / `user-input-to-account-state-meta`** — Confirm the meta/option key governs access or account state (not a cosmetic preference) and the value is genuinely attacker-chosen, not validated against an allowlist or overwritten by a server authority before use. A request value merged into a server-fetched structure is in scope only if the request-controlled element actually alters the privileged state. `intval()`/`absint()` do not neutralize a logic-value choice.

45. **`DISABLED_AUTH_FACTOR_UNCONDITIONAL_TRUE` — substitute-factor FP:** A disabled/negated auth-factor toggle is a false positive when a DIFFERENT verified factor still gates the request in the disabled branch — e.g. an OAuth 2.1 public-client flow skipping client-secret authentication (`auth_method === 'none'`) while PKCE's `code_verifier` is still `hash_equals()`-compared is spec-compliant, not a missing check. Confirm the substitute factor is an actual cryptographic comparison (not merely present-but-unchecked) before dismissing.

### Nonce verification bypass rules

18. **Nonce verification bypass** — `check_admin_referer()`/`check_ajax_referer()` with `$stop = false` (3rd arg) + unchecked return = verification bypassed. Nonce scoped to field type without object ID = reusable across objects.
   - Method-conditional auth bypass: auth wrapper that checks nonce or capability only inside a POST-method conditional returns `true` for all other methods. State-changing GET routes are fully unauthenticated regardless of POST nonce logic.
     - When the sink is a direct `wp_set_auth_cookie()`/`wp_set_current_user()` call rather than a boolean gate wrapper (the OAuth/social-login GET-callback shape), this is Login CSRF (CWE-352→CWE-287), not a generic missing-auth finding — Semgrep `claude.php.wordpress.access-control.conditional-nonce-post-only-auth-cookie` flags it, but only when the sink call is in the SAME function as the conditional, so also check a sibling helper method when the dispatcher alone shows no direct sink.
   - Checking nonce PRESENCE only (`isset($nonce)` / `!empty($nonce)`) without calling `wp_verify_nonce()` = zero cryptographic verification; treat the endpoint as nonce-free when categorizing auth floor.
   - String `'true'`/`'false'` from ternary assignment (`$flag = (condition) ? 'true' : 'false'`) checked with `if (!$flag)`: non-empty strings are truthy in PHP, so `!'false'` evaluates to `false` and the guard never fires. When a nonce or capability gate appears suspiciously permissive, read the assignment source of its boolean guard variable.
   - Same bug via a function return instead of an assignment: a custom auth-wrapper method whose actual return value is the capability-name STRING (intended to be passed INTO `current_user_can($cap)`, not evaluated for truthiness itself) used directly as `if (!Wrapper::method())` never fires, since any non-empty capability string is truthy — verify the wrapper's own return statements before trusting a `!wrapper_call()` guard.
   - `check_ajax_referer($action)` called without a second argument reads `_ajax_nonce` or `_wpnonce` POST/GET fields, not a field named `nonce`; a PoC or live test sending `nonce=<value>` returns -1 and may cause false dismissal of the finding. Confirm the second argument presence before concluding non-exploitable.
   - A nonce or capability check wrapped in `if (is_user_logged_in()) { ... }` without an `else` rejecting the request is silently skipped for anonymous visitors on nopriv endpoints — verify auth checks run unconditionally, not inside a logged-in conditional.
   - Return-value-discarded variant (distinct from the truthy-string bug above — here NO check of any kind exists at the call site): a custom nonce-wrapper method computes and `return`s a pass/fail signal, but a sibling handler invokes it as a bare statement and never consults the result, falling through into state-changing logic regardless of nonce validity (→ Semgrep `custom-nonce-wrapper-result-ignored`). First read the wrapper's own body: if it unconditionally `exit()`s/`wp_die()`s on failure it is self-halting and a bare call is safe; only a wrapper that merely `return`s requires every caller to check it.

50. **REST missing nonce check ≠ automatic CSRF** — → See Tier 4B (Core's `rest_cookie_check_errors()` uid-0 demotion); REST-specific, does not extend to the admin-form/AJAX rule.

## Adversarial draft-status / `parse_args` patterns (absorbed from Group adv)

Group adv was collapsed; its access-control patterns are analyzed here (the two grep
sections `WP_QUERY_DRAFT_STATUS_AJAX` and `WP_PARSE_ARGS_WRONG_ORDER` now ship in
`AUDIT_DIR/grep/group-ac-results.md`). The race-condition / "Beyond the Checklist"
half moved to the Chain pass (`vuln-audit-chain.md`).

**`WP_Query`/`get_posts` with `post_status` including a non-public status — authenticated AJAX and REST:** When a `wp_ajax_` (Contributor+) or REST handler runs a `WP_Query` that explicitly lists `'post_status' => ['publish','draft']` (or any non-public status), all matching posts from ALL authors are returned unless `'perm' => 'readable'` is ALSO set AND the requested status is `private`. `perm=readable` only author-scopes `private` — `draft`, `pending`, `future`, and `trash` remain unrestricted even with `perm=readable`. A Contributor+ handler returning draft posts from all authors without `perm=readable` (or with it but listing `draft`) is an IDOR information disclosure (CWE-862 + CWE-200). The `WP_QUERY_DRAFT_STATUS_AJAX` grep covers both array-literal (`'post_status' => 'any'`) and array-assignment (`$args['post_status'] = 'any'`) syntax. Apply the same analysis to `get_pages()` with non-public `post_status` — it wraps `WP_Query` with identical behavior. Interpret `WP_PARSE_ARGS_WRONG_ORDER` hits with the same access-control lens (see FP rule 8 on `wp_parse_args` argument order).

> ⚠️ Per global CLAUDE.md, read-only disclosure of non-public *post/CPT* content is OOS/CVE-only regardless of auth. Only pursue when the resource is user/customer PII or the flaw yields a state change / auth impact, not bare draft-post content disclosure.

**Draft-status FP verification (before reporting):** confirm (1) handler auth floor ≤ Contributor — a `manage_options`/`edit_others_posts` gate makes "all drafts visible" expected; (2) `post_status` includes ≥1 non-public status; (3) draft/pending content is actually returned in the response body, not fetched for internal logic (count, redirect, cron) and discarded; (4) other authors' drafts are included — a `post_author => get_current_user_id()` restriction to own posts is a FP.
