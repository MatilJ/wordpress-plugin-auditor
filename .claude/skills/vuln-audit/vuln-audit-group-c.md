## Tier 5 — HTML Injection in Server-Side Renderers (CVSS 6.5–8.0) — SSRF component OOS

> **SSRF (CWE-918) is Out of Scope (current program policy).** Analyze server-side renderer sinks (mPDF, wkhtmltopdf, DOMDocument) only for non-SSRF impacts: Local File Read via `file://` protocol (where content is extractable — not the mPDF blind case), HTML injection leading to content manipulation in generated PDFs. Do NOT confirm Blind SSRF findings from renderer sinks. Forward SSRF-only leads to leads-forward.md as OOS/informational.

Use GREP_RESULTS `TIER5_HTML_RENDERERS` (or `AUDIT_DIR/grep/group-c-results.md` in file-based mode). User-controlled data in PDF/image/HTML renderer without `esc_html()`/`strip_tags()`: analyze for non-SSRF impacts only (SSRF is OOS).

**mPDF-specific notes (verify bundled version via `composer.json` or vendor path):**
- **mPDF ≥ 8.x (`CurlHttpClient` architecture):** No `allowRemoteFiles` config key exists — remote fetch is unconditional for any URL containing `://` in `<img src>`. Any `WriteHTML()` call with user-controlled HTML triggers outbound HTTP GET from the server. Flag as Blind SSRF.
- **`file://` trap:** `file://` appears in mPDF's default `whitelistStreamWrappers` and passes `isPathLocal()` — cURL fetches the file. However `ImageTypeGuesser::guess()` returns `null` for non-image content, which the image processor silently discards. File content is never embedded in the PDF output. Do NOT escalate to Local File Read; flag as Blind SSRF only.
- **`esc_html()` does not protect mPDF render sinks:** HTML entity encoding (`&lt;img src=&quot;http://...&quot;&gt;`) is decoded by mPDF's HTML parser at render time back to `<img src="http://...">`. When the HTML renderer reads DB-stored values that had `esc_html()` applied at write time, the SSRF is still triggerable.
- **mPDF ≤ 7.x:** `allow_local_files` config controls local file access; `allowRemoteFiles` may exist — check bundled version's `ConfigVariables.php` for the actual config keys present.

**Tier 8 boundary — SSRF is OOS.** Calls to `wp_remote_*`, `wp_safe_remote_*`, `download_url()`, `fetch_feed()`, `getimagesize($url)`, `get_headers($url)`, or `file_get_contents($url)` appearing in the surface or grep results during Tier 5 analysis are OOS as SSRF findings (current program policy). Do not forward them to Group D1 as in-scope leads. Note them as OOS/informational in leads-forward.md only if they serve as chain primitives for non-SSRF vulns.

## Tier 6 — Stored / Reflected XSS (CVSS 5.4–6.5, escalatable)

Use GREP_RESULTS sections `TIER6_UNESCAPED_OUTPUT`, `SCRIPT_BLOCK_ECHO`, `JS_CONTEXT_PHP_ECHO`, and `ESC_URL_RAW_JS_CONTEXT_ECHO` (`echo esc_url_raw(...)` in a file that also has an inline event-handler/`<script>` context — `esc_url_raw()` is a redirect/DB-storage sanitizer, not a display escaper, and does not neutralize a JS-string-breaking quote; a common source feeding it is `add_query_arg()`/`remove_query_arg()` called with no base-URL argument, which reflects `$_SERVER['REQUEST_URI']` unencoded — confirmed vulnerable pattern, CWE-79).

Also check `SPRINTF_POSITIONAL_ARG_UNESCAPED` — `sprintf()`/`printf()` calls using numbered placeholders (`%1$s`, `%2$s`, ...), the WP i18n form for translatable strings with 2+ substitutions. `TIER6_UNESCAPED_OUTPUT`'s line-level `esc_html|esc_attr` exclude check can false-negative here: one argument may legitimately be wrapped (e.g. `esc_url()` around a `%1$s` link href) while a sibling `%2$s` argument on the same line is not — verify each substituted argument independently rather than trusting an escaping call found anywhere on the line.

| Context | Required | Common mistake |
|---|---|---|
| HTML text node | `esc_html()` | None |
| HTML attribute | `esc_attr()` | `esc_html()` |
| JS string (quoted) | `esc_js()` or `wp_json_encode()` | `sanitize_text_field()`, or any HTML sanitizer (`wp_kses()`, `wp_kses_post()`, `strip_tags()`) — none touch `$`/`{`/`}`/quotes |
| JS value (unquoted) | `wp_json_encode()` or cast | `sanitize_text_field()` |
| URL (`href`/`src`) | `esc_url()` | `esc_attr()` |
| CSS | `esc_attr()` + validation | Nothing |

→ See CANON:sanitize-text-field-limits — NOT sufficient for JS context.
`esc_js()` safe only inside already-quoted JS string. `esc_url()` strips `javascript:` — move on. `wp_kses()` misconfiguration: check allowed tags for `onclick`/`onerror`/`<script>`.

A custom (non-WP-Core) input-filtering function with a reassuring name (containing "sanitize"/"filter"/"clean") may strip only non-printable control characters, passing every HTML/JS-significant character (`'`, `"`, `<`, `>`) through unmodified — common in plugin-bundled code that reimplements request filtering outside WP Core (installers, standalone utilities, migration tools). Read the actual character class the function strips/allows before trusting the name, especially before dismissing a JS-string-context sink as protected.

XSS escalation via `fetch('/wp-admin/user-new.php')` → parse `_wpnonce_create-user` → POST `role=administrator`: admin-context XSS fires immediately (CVSS ~9.8); frontend Stored XSS escalates when an admin visits the page while authenticated (same-origin fetch carries session cookies, CVSS ~8.0, UI:R). Always evaluate frontend Stored XSS for the admin-creation chain — do not skip because the XSS fires on a public page.

### Stored XSS — two-phase analysis

**Phase A — Find low-privilege writes:**

Use GREP_RESULTS `AJAX_HOOKS` (nopriv), `STORED_XSS_WRITES`, `NONCE_RENDER_CONTEXT`, `SAVE_POST_HOOKS`, `WC_BILLING_FIELD_READS` (WooCommerce order billing/shipping fields read without escaping — second-order XSS source when the write path is WC checkout), `CUSTOMER_MODEL_PROPERTY_UNESCAPED_RETURN` (API-backed/"headless" commerce plugins expose the same class of customer-controlled checkout data as magic-getter properties — `$customer->name`/`$customer->email` — rather than WC's `get_billing_*()` methods; this section specifically catches the `return`-based sink shape a `WP_List_Table::column_*()` callback uses, which `TIER6_UNESCAPED_OUTPUT` misses since that section only matches `echo`/`print`/`printf`), `WP_USER_PROFILE_FIELD_RAW_ACCESS` (WP_User `first_name`/`last_name`/`nickname`/`user_nicename`/`display_name` — editable by the account owner via their own `wp-admin/profile.php`, so any authenticated role including Subscriber controls the value; `->data->FIELD` access is a stronger signal than the plain magic-getter form since it bypasses `WP_User::__get()`'s `sanitize_user_field()` filtering entirely — high noise, most hits are non-HTML metadata-array builds, confirm the field reaches an HTML/attribute-rendering sink before flagging).

`save_post` fires for ANY user with `edit_post($id)` — Contributors trigger it. Plugin callbacks commonly store `$_POST` as post meta with `sanitize_text_field()`. For HTML body/attribute injection, XSS requires a literal `<` byte — sanitizer must be weaker than `sanitize_text_field()` (no sanitizer, `wp_unslash()` only, `sanitize_textarea_field()` for HTML-allowing fields). **Exception — URL context:** When the stored value renders in an `href`/`src` attribute via `esc_attr()` instead of `esc_url()`, `sanitize_text_field()` IS insufficient: `javascript:alert(1)` contains no `<` and passes through unchanged; see context table and CANON:sanitize-text-field-limits.

→ See CANON:entity-encoding — entity-encoded payloads are NOT executable in standard HTML output.

**Page-builder module props (shortcode attributes in post_content):** Contributor+ writes module URL fields (Divi `$this->props`, Elementor `$settings`, Beaver Builder `$settings`) as shortcode attribute values in `post_content`. `wp_kses_post()` does NOT strip `javascript:` from shortcode attribute text — kses parses HTML structure, not shortcode parameter values. If the module render method outputs the prop in `href`/`src` via `sprintf()` or concatenation without `esc_url()`, this is confirmed Stored XSS. Scan all module render methods for URL-context output of props without `esc_url()`.

**Elementor `$settings[...]` in HTML attribute context (TEXT controls):** Use GREP_RESULTS `ELEMENTOR_SETTINGS_ATTR_CONCAT` to surface `$settings[...]` values concatenated into HTML attribute strings without `esc_attr()`. For each hit, identify the control type via `add_control()` in the same widget class — TEXT/TEXTAREA controls accept arbitrary user input; SELECT/SWITCHER/SLIDER/COLOR controls are developer-constrained (see FP rule 17). When a TEXT control value is placed inside a double-quoted HTML attribute via direct concatenation (e.g., `'data-attr="' . $settings['key'] . '"'`) without `esc_attr()`, a stored `"` breaks attribute context — confirmed Stored XSS regardless of `wp_kses_post()` applied at save time.

**Also audit `save_post` callbacks for missing capability checks (Tier 4 angle).** Callback processing `$_POST` with privileged side effects (workflow, email, status change) without `current_user_can()` = Missing Authorization (CWE-862). Compare against siblings: inconsistent capability check = likely unintentional.

**Phase B — Find where stored values render in privileged contexts:**

Use GREP_RESULTS `STORED_XSS_READS`, `META_BOX_REGISTRATIONS`, `POST_INSERT_UPDATE`, `CUSTOM_VALUE_GETTERS`, `LIST_TABLE_COLUMNS`, `KSES_ECHO_PATTERNS`, `TITLE_OUTPUT`, `THE_AUTHOR_META_OUTPUT`.

**Custom table second-order reads (`WPDB_RESULT_UNESCAPED_OUTPUT` grep section):** Plugins using custom database tables (common in form builders, booking systems, CRM, review/testimonial, analytics plugins) store user input via `$wpdb->insert()` in Phase A, then render it in admin dashboards via `$wpdb->get_results()`/`$wpdb->get_row()` without escaping. The `STORED_XSS_READS` section only covers WordPress meta/option API reads — custom table reads require separate analysis. For each `WPDB_RESULT_UNESCAPED_OUTPUT` hit: (1) identify the table and column being rendered, (2) trace backward to the write path for that table/column, (3) verify whether the write path sanitizes with `sanitize_text_field()` (strips `<` but `"` survives — insufficient for attribute context) or nothing, (4) verify whether the render path uses `esc_html()`/`esc_attr()` at output. The multi-step write flow FP caveat applies: model/hydration methods may overlay sanitized meta values onto raw columns.

`wp_kses()` scans for literal `<` bytes only. → See CANON:entity-encoding — entities pass through but are NOT executable.

`wp_insert_post()` KSES bypass: applies KSES only when user lacks `unfiltered_html`. Admins/Editors → `post_content` stored verbatim.

**WP user name fields sanitized at core level.** `wp_insert_user()` fires `pre_user_*` filters: `sanitize_text_field()` + `wp_filter_kses()` + `_wp_specialchars()`. Only bypass for HTML context: calling `update_user_meta()` directly.
   - Exception for JS context: `_wp_specialchars()` is called with `ENT_NOQUOTES`, which does NOT encode `"`. Author profile fields (nickname, display_name, etc.) retain literal `"` even after the standard write path. When `the_author_meta()` or `echo get_the_author_meta()` renders the value inside a double-quoted JS string, a `"` in the stored value breaks out of the string literal — confirmed Stored XSS. Use `THE_AUTHOR_META_OUTPUT` and `STORED_XSS_READS` grep sections; require `esc_js()` for JS context.

**Canonical Stored XSS chains:**

Chain 1 — nopriv AJAX + meta render: `wp_ajax_nopriv_` → `wp_unslash($_POST['x'])` only → `update_post_meta()` → admin opens → `echo get_post_meta()` without `esc_html()` → literal `<script>` fires.

Chain 2 — shortcode form + direct echo: `[shortcode]` public page (no auth) → raw `$_POST` → `$wpdb->insert()` → admin list → `echo $row->field` → XSS.

Chain 3 — server-side entity decode: any write → `sanitize_text_field()` → stored with entities → admin view → `html_entity_decode($val)`, `htmlspecialchars_decode($val)`, or `wp_specialchars_decode($val)` → `echo` → literal `<` in HTML → XSS. ONLY scenario where entities become executable. Use `WP_SPECIALCHARS_DECODE` grep section (self-reassignment sub-pattern `$X = html_entity_decode($X)` is the highest-signal shape — same-scope reversal of a preceding tag-stripping call).

Chain 3B — `wp_kses_post()` HTML comment + base64 decode: Contributor stores `<!-- prefix BASE64_PAYLOAD -->` in `post_content` → kses preserves (alphanumeric content, no tags) → `the_content` filter → `preg_replace_callback` → `base64_decode()` → decoded HTML/JS → Stored XSS. Detection: `preg_replace_callback` on comment pattern + `base64_decode()` in closure.

Chain 5 — AJAX `echo` + `wp_die()` HTML content-type: AJAX handler uses `echo $data; wp_die();` instead of `wp_send_json()`. WP Core `_ajax_wp_die_handler()` (functions.php:4057) does NOT set a Content-Type header — browser defaults to `text/html`, rendering any HTML/script in the echoed data. By contrast, `wp_send_json()` (functions.php:4542) explicitly sets `Content-Type: application/json` before output. Detection: use `AJAX_ECHO_WP_DIE` grep; trace data from `$_POST`/`$_GET` through to `echo` in `wp_ajax_*` / `wp_ajax_nopriv_*` callbacks. Confirm: (1) no `header('Content-Type: application/json')` before the echo; (2) no `wp_send_json*()` wrapper; (3) user-controlled data reaches the `echo` without `esc_html()`. If `nopriv` → Reflected XSS (CVSS 6.1); auth-required → lower.

Chain 6 — `add_query_arg()` reflected XSS: `echo add_query_arg(...)` or output in `href`/`action` attribute without `esc_url()` wrapper. `add_query_arg()` returns a raw URL string with zero escaping — when called without an explicit base URL argument, it injects the current `$_SERVER['REQUEST_URI']` including attacker-controlled query parameters. Detection: use `ADD_QUERY_ARG_ECHO` grep + Semgrep `add-query-arg-unescaped`. FP filter: `esc_url(add_query_arg(...))` is safe; `esc_url_raw(add_query_arg(...))` is safe for DB storage but NOT for HTML output. Most common in pagination links, admin page URLs, and form `action` attributes.

Chain 7 — HTTP header storage XSS: Plugin stores `$_SERVER['HTTP_REFERER']`, `$_SERVER['HTTP_USER_AGENT']`, or `$_SERVER['HTTP_X_FORWARDED_FOR']` into DB (often via `update_option()`, `$wpdb->insert()` in analytics/logging tables) without sanitization. Admin views the stored data in a dashboard/log viewer without `esc_html()`. HTTP headers are fully attacker-controlled — `Referer` and `User-Agent` accept arbitrary HTML/JS payloads. Detection: use `HTTP_HEADER_DB_WRITE` grep section + Semgrep `http-header-to-db-write`; for each hit, trace the stored value forward to admin render paths (custom admin pages, list tables, dashboard widgets). Common in analytics, SEO, security/logging, and visitor-tracking plugins. FP filter: `sanitize_text_field()` at write time prevents literal `<` storage; `esc_url_raw()` for Referer URLs prevents angle brackets. Also verify admin render path escaping — even write-sanitized values need `esc_attr()` in attribute contexts.

Chain 8 — Admin notice flash message XSS: Plugin stores settings values via `update_option()` or transient, then renders them in an `admin_notices` hook callback without escaping. Common patterns: `printf('<div class="notice"><p>%s</p></div>', get_option('plugin_setting'))` or `<input type="text" value="<?php echo get_option('field'); ?>">` in admin settings HTML. Admin notices fire on EVERY admin page load for ALL admin users — a single stored XSS in a notice callback has maximum admin reach. Detection: use `ADMIN_NOTICE_UNESCAPED_OUTPUT` grep section + Semgrep `admin-notice-unescaped-option-output`; cross-reference with `TIER4_OPTION_WRITES` to identify write paths. Also check `$_GET`/`$_POST` parameters rendered in admin notices (flash messages after form submission) without escaping — this is reflected XSS in an admin context. FP filter: `esc_html()` or `esc_attr()` wrapping the value in the notice HTML.

Chain 9 — Filename/upload metadata XSS: Plugin renders uploaded filenames or attachment metadata without escaping. Patterns: (a) `echo basename($file_path)` where `$file_path` contains user-controlled filename, (b) `echo $attachment->post_title` where title was derived from upload filename, (c) custom upload handlers storing `$_FILES['name']` and later rendering it in admin file lists or download pages. Detection: use `FILENAME_METADATA_OUTPUT` grep section + Semgrep `filename-metadata-unescaped-output`. FP filter: WP Core's `media_handle_upload()` passes filenames through `sanitize_text_field()` + `title_save_pre` chain (see FP rule 13); only custom upload handlers bypassing the WP media pipeline are vulnerable. `sanitize_file_name()` at write time restricts to `[a-zA-Z0-9._-]` — safe.

Chain 10 — Length-only validation mistaken for sanitization: `strlen($_GET['x']) == 32` (or similar fixed-length gate, often guarding an MD5-shaped token/nonce parameter) is a shape check, not a character-class allowlist or an output escape — any 32-byte payload containing `"`, `<`, `>` still passes. Common in procedural plugins that then concatenate the "validated" value unescaped into a `define()`-built self-URL/token constant reused across later HTML attributes or JS strings, or into any other unescaped output. Detection: use `LENGTH_ONLY_REQUEST_VALIDATION` grep section; manually trace the gated value forward to its output sink(s) — no Semgrep companion exists (an OSS Semgrep taint-tracking limitation was confirmed empirically: a later write to a sibling key of the same multi-level nested array/global clears prior taint facts for other keys of that array, defeating dataflow tracking through the common "stash into a config array, read back out several statements later" idiom, even with `symbolic_propagation: true`). FP filter: a regex allowlist (e.g. `preg_match('/^[0-9a-f]{32}$/', ...)`) or an escaping function wrapping the value at every output site is safe; a length check used purely for an array-key lookup (not reaching output) is safe.

Chain 11 — Plugin-defined template-tag/merge-tag engine, per-resolver raw request echo (→ core SKILL.md FN Prevention #10): Plugins implementing their own `{tag:key}`-style substitution engine (common in form builders, page builders, notification/email systems) register each tag as a name → resolver-closure pair. The overall echo of the tag-substituted template/message field will not surface via a simple `$_REQUEST`-to-`echo` taint rule, because the taint enters several call frames away, inside an individual resolver, then gets spliced back into an otherwise-innocuous-looking template string by the engine's own substitution/replace step. A second, equally common engine shape reassigns the template string in place via `str_replace($token, $resolved_value, $template)` rather than returning the resolved value directly — e.g. a `{{GET:name}}`/`{{COOKIE:name}}`-style dynamic-placeholder handler. Detection: find the tag-registration call (`add_tag(`, `register_tag(`, or an array literal with a `'resolver'`/`'callback'` key mapped to a closure) and read EVERY individual resolver body — a resolver whose body is `return $_REQUEST[$key];`/`return $_GET[$key];` (or a thin one-line wrapper) with no escaping is the root cause regardless of how many render call sites eventually consume it (Semgrep `tag-resolver-raw-request-return` covers the direct-return, str_replace-in-place, AND wp_kses()-intermediate-assignment forms — the last is a third, equally common shape that stages the superglobal in a variable via `wp_kses($val, 'post')`, a tag-syntax filter that leaves quotes untouched, before the engine's own template-substitution step consumes it several statements later); for the str_replace shape also use the `MERGE_TAG_SUPERGLOBAL_STR_REPLACE_UNESCAPED` grep section, for the wp_kses()-assignment shape use `MERGE_TAG_WP_KSES_SUPERGLOBAL_ASSIGN`. Then enumerate every place the templated field (custom render/message/success templates, notification bodies) is echoed — these engines typically escape only their OWN delimiter syntax (`{`/`}`, to prevent re-parsing) and apply zero HTML-encoding to resolved values, so every echo site downstream of an unescaped resolver is a reflected (or stored, if the template itself is DB-persisted) XSS sink. FP filter: the resolver wraps its return in `esc_html()`/`esc_attr()`, or the tag name maps to a server-computed value (site option, current date) rather than a superglobal. **`sanitize_text_field()` is NOT a valid FP filter here** — it strips tags but not quotes/backslashes, so it does not neutralize the value for a `<script>`/JS-string sink or an unquoted/single-quoted HTML attribute the engine's own render sites may use; confirmed exploitable end-to-end via exactly this gap (a page-builder's Custom-JS `<script>` echo of a `{{GET:}}`/`{{COOKIE:}}`-substituted, `sanitize_text_field()`-only value). Only treat `sanitize_text_field()` as sufficient when every consuming render site is confirmed to be a plain HTML text node.

Chain 12 — `json_encode()`/`wp_json_encode()` into an HTML comment (comment-breakout via literal `-->`, not attribute-quote breakout — `esc_attr()`/`<script>`-context safety does not transfer to comment context). Detection: `JSON_ENCODE_HTML_COMMENT_BREAKOUT` grep section + Semgrep `json-encode-html-comment-breakout`; verify at least one encoded field is user-controllable before confirming.

Chain 13 — URL sanitizer context mismatch: `sanitize_url()`/`esc_url_raw()` (`sanitize_url()` is an alias of `esc_url_raw()` since WP 5.9) used where `esc_url()` belongs. Both skip the `'display'`-context step that HTML-entity-encodes a literal `'`, so the result remains unsafe when spliced into a single-quoted `href`/`src` attribute — double-quoted attributes are unaffected, since the shared character-class filter strips `"` unconditionally regardless of context.
```php
$link = sanitize_url( $atts['url'] );
echo "<a href='{$link}'>"; // ' survives — attribute breakout
```
Detection: `ESC_URL_RAW_ATTR_CONTEXT_SPLICE` grep section + Semgrep `esc-url-raw-html-attribute-misuse`. FP filter: safe when the sanitized value is written only to the database or a redirect target and never echoed into markup, or when the attribute is double-quoted.

Chain 14 — Asymmetric URL-component re-encoding: code splitting a URL via `wp_parse_url()`/`parse_url()` commonly re-encodes the query string on reassembly (`parse_str()` + `urlencode_deep()`/`build_query()`) but treats the `'fragment'` key as a bare structural marker, re-prefixing it with `'#'` and splicing it back with no encoding.
```php
$parts = wp_parse_url( $url );
$parts['fragment'] = '#' . $parts['fragment']; // never encoded
```
Detection: `PARSE_URL_FRAGMENT_UNESCAPED_REASSEMBLY` grep section + Semgrep `parse-url-fragment-unescaped-reassembly`. FP filter: safe when the fragment is `rawurlencode()`'d/`esc_attr()`'d before the `'#'` concatenation, or the reassembled URL is never echoed into HTML markup.

### Widget save→render XSS chain

`WP_Widget::update()` stores `$new_instance` values (admin input) → `WP_Widget::widget()` renders `$instance` values on the frontend/admin. `update()` commonly sanitizes with `sanitize_text_field()` or `strip_tags()` — sufficient for HTML body context but NOT for attribute, URL, or JS contexts. Detection: use `WIDGET_RENDER_OUTPUT` grep; for each `$instance[` access in `widget()` method, verify escaping matches the output context. Common miss: URL fields stored with `sanitize_text_field()` (allows `javascript:` — no `<` to trigger tag stripping) rendered in `href` without `esc_url()`. FP filter: `esc_html($instance['title'])` is safe for text nodes; `esc_url($instance['link'])` is safe for href.

### Block attribute XSS — Contributor-accessible

Block attributes stored as JSON in HTML comments. `wp_pre/post_kses_block_attributes()` preserves JSON structure. Attribute VALUES containing HTML are still kses-filtered for users without `unfiltered_html`: event handlers stripped, `<script>` removed, `javascript:` stripped.

**HIGH-CONFIDENCE vector — attribute context breakout (no HTML needed, kses-irrelevant):**

Chain 4a — double-quote attribute breakout: `{"url":"\" onfocus=alert(1) autofocus x=\""}` → kses preserves (no `< >`) → `echo '<a href="' . $attributes['url'] . '">'` → XSS.

Chain 4b — script context: `{"config":"</script><script>alert(1)</script>"}` → verify `</script>` survives encoding. **Note:** PHP `json_encode()` default escapes `/` → `\/`, so `</script>` becomes `<\/script>` (HTML5 parsers do NOT treat this as a script end-tag) — this breakout is blocked when data passes through `json_encode()`. **Exception: `JSON_UNESCAPED_SLASHES` removes this protection** — when `wp_json_encode($data, $flags)` includes `JSON_UNESCAPED_SLASHES`, forward slashes pass through unescaped and `</script>` terminates the enclosing block. Use `JSON_UNESCAPED_SLASHES_ENCODE` grep results; `JSON_HEX_TAG` neutralizes both the breakout and any `innerHTML` sink — confirm it is absent before flagging. When `</script>` is blocked (no `JSON_UNESCAPED_SLASHES`), trace the JS consumer for `dangerouslySetInnerHTML`, `innerHTML`, or `document.write` sinks — `<img src=x onerror=alert(1)>` (no forward slashes) passes through `json_encode()` unmodified and executes when inserted into the DOM via these sinks.

Chain 4c — `javascript:` protocol: `{"link_url":"javascript:alert(1)"}` → only if no `esc_url()`.

Chain 4d — `json_encode` into single-quoted data attr: `json_encode($attrs)` without `JSON_HEX_APOS` in `data-attributes='{$encoded}'` → literal `'` terminates attribute → event handler injection. No HTML tags needed. → See CANON:sanitize-text-field-limits — `'` passes through. Fix: `JSON_HEX_APOS|JSON_HEX_QUOT|JSON_HEX_AMP` or `esc_attr()`. Semgrep misses `return` sinks — look for `json_encode(`/`wp_json_encode(` in `render_callback` return values.

Chain 4d-iii — indirect wrapper-method variant of 4d: a getter/helper whose name contains "json" (e.g. `getJsonDescription()`) internally builds and returns the `json_encode()` result, and the *caller* echoes that bare method call into a single-quoted attribute with no `esc_attr()`/`esc_html()` wrap. `JSON_ENCODE_SURFACE` only matches a literal `json_encode(`/`wp_json_encode(` token on the line and misses this shape entirely; use `JSON_WRAPPER_METHOD_ECHO` instead. Missing `JSON_HEX_AMP` specifically (APOS/QUOT/TAG present) is a variant of this chain: an HTML entity in the source data (e.g. `&#39;`) survives the encode untouched and the browser's own attribute-value character-reference decoding turns it back into a literal `'` at render time — check for this even when APOS/QUOT/TAG are all present, since AMP is the one flag developers most often forget.

Chain 4d-ii — `json_encode` into double-quoted HTML attribute (string concatenation): `json_encode($obj)` placed into `$out .= $key . '="' . $value . '"'` → JSON structural `"` characters (around object keys and string values) terminate the double-quoted attribute boundary → attacker-controlled JSON key names such as `" onmouseover=alert(1) x="` inject directly as live HTML event-handler attributes. `JSON_HEX_APOS` does NOT protect here — it encodes `'` but not `"`. `JSON_HEX_QUOT` encodes `"` → `"` within string values but JSON object key delimiters are still literal `"`. Fix: `htmlspecialchars()` or `esc_attr()` on the encoded value before concatenation into the attribute string. Detection: use `JSON_ENCODE_SURFACE` hits; trace whether the encoded value is concatenated into `'="' . $value . '"'` without intervening `esc_attr()`/`htmlspecialchars()`. Also check `foreach ($array as $k => $v) { $out .= ' ' . $k . '="' . $v . '"'; }` where `$v` originated from `json_encode()`.

The pattern also applies to meta box PHP templates: `echo json_encode(get_post_meta(...))` in `value='...'` or `data-*='...'` attributes is a second-order stored XSS sink when a `save_post` hook writes unfiltered `$_POST` data to the same meta key. Cross-reference `JSON_ENCODE_SURFACE` hits in meta box template files against `SAVE_POST_HOOKS` and `STORED_XSS_WRITES`.

Chain 4e — PHP data-attrs → JS rendering: PHP `wp_json_encode($attrs)` → `get_block_wrapper_attributes(['data-attrs' => $json])` → HTML-encodes for attribute. Browser HTML-decodes at read time → JS receives raw values → `innerHTML = \`<img src="${atts.field}">\`` → XSS. Also applies when JS framework renders data-attr JSON fields as element props: Preact/Vue `createElement('a', {href: field})` / `S("a", {href: field})` renders `javascript:` URLs in href without sanitization (React 17+ strips `javascript:`; Preact and Vue do not). PHP `htmlentities(ENT_QUOTES)` on the data-attribute protects the HTML attribute boundary only — it does NOT sanitize URL schemes within JSON string values, and the downstream JS-rendered href is the actual sink. Check `block.json` for `"type":"object"` without `"additionalProperties":false` — accepts arbitrary keys. URL/image fields omitted from `escapeAttribute()` = gap.

**Detection:**
1. Find `register_block_type()` / `register_block_type_from_metadata()`
2. Locate `render_callback`; trace `$attributes[$key]` access + `json_encode($attributes)` calls
3. Classify output context: HTML attribute (high confidence), script context (high), URL attribute (high if no `esc_url()`), HTML body (low — verify kses behavior)
4. Check JS view files (`block-view.js`, `view.js`, `frontend.js`) and compiled/bundled JS (`build/**/*.js`, `assets/frontend/**/*.js`) for `dataset.*` reads → template literals/`innerHTML`/virtual DOM `href`–`src` props without `escapeAttribute()`/URL scheme validation; Preact and Vue do not filter `javascript:` from `href` props (React 17+ does)
5. Check `block.json` for `"type":"object"` without `"additionalProperties":false`
6. Check escaping: `esc_html()`/`esc_attr()`/`esc_url()`/`wp_kses_post()`

Use GREP_RESULTS `BLOCK_ATTRIBUTE_OUTPUT`. This section also now matches `$instance[...]`/`$field[...]` — the same unescaped-settings-array-value shape for widget instance settings (`WP_Widget::widget()`) and form/module field settings arrays; trace these to their own render sink (often `sprintf()`/`.=` string-building rather than a direct block `render_callback`) rather than assuming Contributor-only reachability.

**Mandatory empirical verification for block attribute XSS:** Code analysis alone insufficient. Steps: (1) set value as Contributor via Code Editor or REST; (2) read stored `post_content` via REST `content.raw`; (3) confirm payload survives; (4) load frontend, confirm JS fires. Without test env: cap confidence at 70%, flag as "requires empirical verification".

### Shortcode attribute as HTML tag name — HIGH confidence

Plugins letting users control wrapper element (`titleformat`, `heading_tag`, `wrapper`) echo value into tag-name position. Payload is plain text → kses irrelevant. `shortcode_atts()` limits KEYS not VALUES.

Chain: `[shortcode titleformat="img src=x onerror=alert(1)//"]` → kses preserves → `shortcode_atts()` preserves → getter returns raw → template `<<?php echo $format ?>>` → XSS.

Detection: find `shortcode_atts()` defaults with keys `*format`/`*tag`/`*element`/`*wrapper`/`*heading`; trace to output; check for `sanitize_key()`/`tag_escape()`/allowlist.

**Block render_callback variant:** Same injection when `$attributes['*Tag']`/`$attributes['*element']`/`$attributes['*heading']`/`$attributes['*Style']` appears at tag-name position — two sub-cases: (a) `esc_attr()` instead of `tag_escape()` — `esc_attr()` passes spaces, `/`, and `=` unchanged; (b) **no escaping at all** — direct string concatenation like `'<' . $var . '>'` or `'</' . $var . '>'` where `$var` was assigned from `$attributes[...]`. Both render `img src=x onerror=alert(1)//` as a valid `<img>` element. Detection: use `BLOCK_ATTRIBUTE_TAG_NAME_SINK` grep section (covers both `<?php echo esc_attr(...)` template patterns and `'<' . $var` concatenation patterns). Also check intermediate variables assigned from `$attributes[...]` that flow into string concatenation without escaping — the grep surfaces `$attributes[...]` access but the tag-name concatenation may use a local variable name.

### Shortcode attribute as separator/glue — HIGH confidence

`implode($atts['glue'], $items)` where the separator comes from a shortcode attribute inserts the unescaped value between every item in the HTML output. Often overlooked because individual items are individually escaped while the glue is not. A telling signal: the parallel `prefix` parameter IS escaped with `esc_html()` while the `glue` parameter is not — inconsistent escaping of structurally equivalent parameters.

Detection: use `SHORTCODE_IMPLODE_SEPARATOR` grep section; for each hit trace whether the first argument to `implode()` / `join()` is escaped before the call or the result is escaped afterward. Verify ≥2 items exist in the array for the separator to render (trivially achievable by the attacker).

**Hand-rolled variant (no `implode()`/`join()` call):** the same separator/glue value can instead be passed as a constructor argument to a custom list/tree renderer (a class extending `Walker`/`Walker_Nav_Menu`/`Walker_Page`/`Walker_Category`/`Walker_Comment`, or a hand-rolled equivalent) and concatenated unescaped between rendered items inside a *different* method than the one that received it (e.g. stored in `__construct()`, concatenated in `end_el()`). `SHORTCODE_IMPLODE_SEPARATOR` does not surface this shape — there is no `implode()`/`join()` call to match.

Detection: use `CUSTOM_LIST_WALKER_CLASSES` grep results to find candidate classes; for each, manually verify the constructor-received value is escaped before every concatenation across all of the class's render methods. This constructor-to-property-to-different-method flow crosses methods via object state rather than a direct call chain — static/taint tooling does not reliably track it (confirmed: a targeted Semgrep rule for this exact shape was tested and failed to fire even on known-vulnerable source), so treat every hit here as requiring full manual trace, not automated confirmation.

### Shortcode attribute as PHP date format string — MEDIUM confidence

`get_the_time($format, $post)` / `get_the_modified_time($format, $post)` where `$format` comes from a shortcode attribute. PHP `date()` passes non-format-code characters through literally — `<` and `>` are not date codes and appear as-is in output, enabling HTML injection. Common footgun: the safe sibling function wraps its call with `esc_html()` while the vulnerable function does not. Use `DATE_FORMAT_UNESCAPED` grep section; verify whether return value is wrapped in `esc_html()`/`esc_attr()`.

### RegExSS — preg_replace HTML attribute stripping → XSS

`preg_replace()` with greedy/lazy quantifiers (`.*?`, `.*`, `.+`, `[^"]*`) used to strip HTML attributes from content. Attackers craft input with mixed quote types (single inside double) to make the regex match across attribute boundaries, promoting injected event handlers (`onfocus`, `autofocus`) into the element. Use GREP_RESULTS `PREG_REPLACE_HTML_ATTR_STRIP` + Semgrep `preg-replace-html-attr-strip`.

**Triage (all must be true):** (1) content is user-controllable (post content, comments, shortcode attrs, form input); (2) regex strips a single attribute (`attr="..."`), not an entire element (`<tag>...</tag>`); (3) no proper escaping (`esc_attr`, `wp_kses`, `wp_kses_post`, `WP_HTML_Tag_Processor`) follows the `preg_replace`; (4) attacker controls quote types in the input (not pre-sanitized to one quote style).

**Safe-dismiss:** BBCode converters (regex contains `\[`), JSON-LD/structured data removal, smiley/emoticon replacement, entire element removal (closing tag present), output post-processed by `wp_kses_post()`/`WP_HTML_Tag_Processor`, or by `DOMDocument` when the FINAL output is the DOM's own `saveHTML()`/`saveXML()` serialization.

**`DOMDocument` is a parser, not a sanitizer — do not blanket-dismiss.** `loadHTML()` HTML-entity-decodes attribute/text values on read (`nodeValue`/`getAttribute()`), so an entity-encoded payload that passed `wp_kses`/regex stripping specifically because it contained no literal `<`/`"` bytes (e.g. `foo.jpg&quot;onerror=alert(1)//`) decodes back to a live `"` once read out of the parsed tree. Only safe-dismiss when the code re-emits the DOM via its own serializer; if it instead reads individual node/attribute values out of the tree and manually re-concatenates them into a new string, this is the same entity-decode-reversal class as Chain 3 above, just via implicit parsing instead of an explicit `html_entity_decode()` call — verify every value read this way is re-escaped (`esc_attr()`/`esc_url()`) before re-emission.

**Multi-step write flows (booking/form/CRM plugins):** Plugins split writes across multiple tables. Model/hydration methods may overlay sanitized meta values onto raw columns, breaking XSS chain. **Mandatory:** when consumer reads via model method (not raw `$wpdb->get_row()`), read model method source. Look for secondary query + meta overlay + sanitization. If overlay exists with sanitized meta write → FP.

**`get_the_title()` / `the_title()` NOT HTML-safe.** Default `the_title` filter callbacks perform text-aesthetic transforms only. But WP core protects `post_title` on save: `title_save_pre` → `wp_filter_kses()` for users without `unfiltered_html`. → See CANON:entity-encoding — entities not executable. Unescaped title = code quality issue, not exploitable XSS, when standard `wp_insert_post()` is the only write path. Only exploitable via direct `$wpdb->update('wp_posts', ['post_title' => $val])` bypassing the save pipeline.

### Second-order Arbitrary Shortcode Execution — write-path triage

Use GREP_RESULTS `DO_SHORTCODE_DB_CONTENT`. When `do_shortcode()`/`apply_shortcodes()` renders DB-stored content (option, post meta, user meta, transient), assess the write path:
- Is the option/meta writable by low-privilege users (nopriv AJAX, Subscriber+, public form)? Trace `update_option()`/`update_post_meta()`/`update_user_meta()` calls for the same key.
- Is the stored value sanitized with `strip_shortcodes()` at write time? `sanitize_text_field()` does NOT strip shortcode syntax — `[tag attr=value]` passes through unchanged.
- If write path is low-privilege and no shortcode stripping at write → confirmed ASE (CWE-94). Forward to Chain agent for impact assessment (what shortcodes are registered, what they expose).
- Wordfence CVSS for second-order ASE: same as direct — 7.3 unauthenticated, 5.4 subscriber+.
- `apply_shortcodes()` is a WP Core alias for `do_shortcode()` (shortcodes.php:223) — treat identically.
- **Immediate self-trigger, not "only once approved/rendered later":** the same write-handler (AJAX comment/form submission, etc.) frequently echoes the just-created record back to the submitter in its OWN response for instant UI feedback, via the identical render path used for normal page loads — check whether this self-render is gated by the same moderation/approval-status check the "later, for other visitors" path uses. When it isn't, the primitive fires unconditionally in the attacker's own request (`UI:N`, no wait for moderation/a third-party view), which is a materially different (and typically more severe/more available) exploit than the "must be approved first" framing.

## Group C — FP Verification Rules

These rules supplement the universal FP rules in the shared core SKILL.md Phase 4. Numbers continue after the core list; rules marked **TP** flag confirmed-vulnerable shapes, not FPs.

11. **Filter-hook-dependent output (`apply_filters()` with user suffix).** FP when `$hook` is validated against an allowlist before `apply_filters()`.
   - When the return is used directly in HTML (e.g. as a tag name) unsanitized, exploitation needs registering a PHP filter hook — code-execution-level (PR:H) → informational only.
12. **jQuery/JS DOM HTML-insertion sinks.** `.html()`/`.append()`/`.prepend()`/`.after()`/`.before()`/`.replaceWith()` and the `$(htmlString)` constructor (incl. `.appendTo()`/`.prependTo()`/`.insertBefore()`/`.insertAfter()`) parse their argument as HTML — functionally `innerHTML`; `.text()`/`.val()`/`textContent` are safe. Use `JQUERY_DOM_INSERTION_SINKS` (+ Semgrep `eval-wrapped-jquery-html-concat` for `eval()`-wrapped bundles).
   - PHP-side escaping is irrelevant in JSON AJAX responses rendered by JS — the browser HTML-decodes `data-*` at read time; trace the JS consumer (`.html()`/`innerHTML` vs `.text()`), not the PHP echo.
   - Check every arm of a layout/display-mode `if`/`else if` render function independently — a sanitizer (`DOMPurify.sanitize()`, `.text()`) on one arm doesn't cover siblings; the same field raw in another arm is the miss.
   - A URL field from `dataset.*` → Preact/Vue `href`/`src` prop is unsanitized (those frameworks do NOT strip `javascript:`; React 17+ does); PHP `htmlentities(ENT_QUOTES)` guards the attribute boundary only, not the scheme.
   - `json_encode()` in a PHP `<script>` block: default slash-escaping (`/`→`\/`) blocks `</script>` but not `<`/`>` — `<img src=x onerror=alert(1)>` still fires via `innerHTML`/`dangerouslySetInnerHTML`/`document.write`; FP when the JSON is passed to a JS parsing API/constructor (consumed as data, not DOM-inserted).
   - The grep exclude filter is defeated on minified/bundled files (whole module on one line, or `eval("...")` webpack wrap) — one safe usage suppresses every sink on that line; manually re-inspect all DOM-insertion calls on anomalously long lines.
   - A plugin-defined JS regex tag-stripper (e.g. a single `.replace(/<[^>]+>/g,'')` pass) feeding `dangerouslySetInnerHTML`/`innerHTML` is safe only when it runs as ONE global-flag pass — a single non-overlapping greedy pass cannot be bypassed by nested-tag concatenation tricks (`<scr<script>ipt>`), but an iterative/multi-pass or non-global strip can; verify the actual regex flags and pass count before dismissing or confirming.
13. **WP-Core write-time sanitization neutralizes unescaped output.** Data passing a Core save/hook pipeline is sanitized before the plugin sees it, so an unescaped echo is a code-quality issue, not XSS — verify the write path is the Core API, not a direct `$wpdb` write.
   - `wp_login_failed`/`wp_login`/`lostpassword_post`/`retrieve_password`: `sanitize_user()`+`strip_tags()` runs before the hook — FP unless the plugin reads `$_POST['log']` directly.
   - Update-checker transients (`update_plugins`/`update_themes`/`update_core`) self-heal every `admin_init` from api.wordpress.org — an overwrite has zero lasting impact; do not report.
   - `save_post`/`delete_post` etc. — Core validates capability before firing; reclassify Semgrep nonce/auth hits as data-quality.
   - `get_the_title()`/`the_title()`, term `name`/`slug` (`pre_term_*`), and attachment `post_title` from `media_handle_upload()` all get write-time `wp_filter_kses()` for users without `unfiltered_html` (→ CANON:entity-encoding); `wp_insert_post()` stores `post_content` verbatim only for `unfiltered_html` roles. Only bypass for HTML: a direct `$wpdb->update` write.
   - **TP exception:** author profile fields (nickname/display_name/…) pass `_wp_specialchars(ENT_NOQUOTES)`, which does NOT encode `"` — `the_author_meta()`/`echo get_the_author_meta()` inside a double-quoted JS string is Stored XSS (`THE_AUTHOR_META_OUTPUT`; require `esc_js()`).
   - **TP exception:** `wp_insert_comment()` performs a bare `$wpdb->insert()` and, unlike `wp_new_comment()`, never invokes `wp_filter_comment()` — `comment_author`/`comment_content` set from request data via this function is stored byte-for-byte unfiltered (grep section `COMMENT_WRITE_KSES_BYPASS_SINKS` flags the sink; verify WP core source before dismissing as core-filtered like its sibling insert functions). **Correction:** `wp_update_comment()` is NOT the same shape — WP core (`wp-includes/comment.php`) DOES call `wp_filter_comment()` from `wp_update_comment()`, conditionally adding `wp_filter_kses` to the `pre_comment_content` filter for any author lacking `unfiltered_html`, so an update-path payload is kses-filtered (`<script>` tags stripped). Confirm which of the two functions the sink actually calls — do not assume update-branch call sites share the insert branch's unfiltered behavior.
   - **FP note — `comment_author` render-side protection:** even when `comment_author` is stored unfiltered via `wp_insert_comment()` above, WordPress core's `default-filters.php` registers `esc_html` on the `comment_author` filter unconditionally (not role/admin-gated), and the standard `comment_author()`/`get_comment_author()` template tags apply it before echoing — raw HTML in a stored `comment_author` value is neutralized on any render path using these template tags. Only a render path reading `$comment->comment_author` directly from the DB object (bypassing the template tag/filter) is exploitable for this specific field; verify which accessor the template actually uses before confirming.
   - Same neutralization logic extends to a plugin's OWN by-design raw-code/script-injection feature (not just Core's `unfiltered_html`): if the same actor tier already has a sanctioned channel to inject equivalent-or-worse content, a sibling escaping gap in a different field of the same feature adds no new capability — confirm the sanctioned channel is reachable at the identical auth floor before dismissing.
14. **Non-HTML sinks & safe-return escapers are not XSS.** `wp_mail()` body (flag only when `$headers` is user-controlled), `wp_send_json*()`, `WP_REST_Response`, `error_log()`, and model returns do not render as browser HTML; `selected()`/`checked()`/`disabled()` return only predefined safe strings.
   - A plugin response-wrapper class that unconditionally sets a JSON Content-Type (verify in its own send method, not from its name) is `wp_send_json`-equivalent — its output is non-HTML.
   - `wp_nonce_url()` wraps its return in `esc_html()`; `esc_url_raw()`/`sanitize_url()` strip `"` and, at write time, literal `<` (not URL-valid) — safe before an unescaped `wp_kses_post()`/`echo` render **only in a double-quoted attribute**. Neither strips a literal `'` (→ Chain 13) — a single-quoted `href`/`src` attribute remains exploitable even after `esc_url_raw()`/`sanitize_url()`.
   - `esc_like()` is safe as a `%s` arg to `prepare()`; **TP** when interpolated into the format string.
   - A value written into a generated XML/CSV/TSV/JSON feed/export FILE (product feeds, merchant catalogs, data exports) is not an HTML-rendering sink regardless of escaping strength — the file is consumed by a feed-reading platform or spreadsheet, never a browser DOM; re-classify only if the same field is also echoed on an admin/frontend HTML page.
15. **kses semantics.** Default `wp_kses()`/`wp_kses_post()` triggers only on a literal `<` — entity-encoded and alphanumeric/base64 HTML-comment payloads pass through but are NOT executable (→ CANON:entity-encoding); the real vector is attribute-context breakout or tag-name position, needing no `<`.
   - **NOT safe:** a custom `$allowed_html` that lists an `on*` event handler preserves it intact — read the array (`KSES_ALLOWED_EVENT_HANDLERS`).
   - **NOT safe:** `wp_kses()` re-parsing a fully-assembled string still admits any `on*` handler, a dangerous URI protocol on a URI attribute, or an unvalidated `style`/`safe_style_css` value (distinct from Chain 4a, where kses never runs on the render path).
   - Block-attribute VALUES are kses-filtered — reliable breakout is double-quote attribute or tag-name position (`'<' . $var . '>'`, or `esc_attr()` at a tag position); `dangerouslySetInnerHTML` needs executable HTML surviving kses at save; CSS `</style><script>` is blocked unless the write path is kses-exempt (meta without `sanitize_callback`).
   - Block JSON containing `>` (arrow fns) may be stripped by kses's regex parser — confirm with a `>`-free payload (`eval(atob('...'))`) before dismissing.
   - `wp_add_inline_style()` prints its CSS buffer between `<style>` tags unencoded — a second-order value reaching it breaks CSS context; `WP_HTML_Tag_Processor::set_attribute()`/`add_class()` escape `<>&"'` internally (safe unless the plugin subclasses it).
   - **NOT safe — wrong-context escaper:** `wp_kses()`/`wp_kses_post()`/`sanitize_text_field()`/`wp_strip_all_tags()`/`strip_tags()` echoed directly inside an open JS string or backtick template literal are HTML-only filters — none touch `$`/`{`/`}`/quotes, so a `${...}` substitution or quote-breakout survives untouched; the correct escaper is `esc_js()`/`wp_json_encode()`. Detection: `JS_CONTEXT_PHP_ECHO` grep section (sanitizer-echo variant) + Semgrep `inline-js-template-literal-raw-echo`.
16. **`json_encode()` into an HTML attribute.** Without `JSON_HEX_APOS|JSON_HEX_QUOT|JSON_HEX_AMP` the structural quotes break attribute context — use `esc_attr()`/`htmlspecialchars()`.
   - In double-quoted concatenation (`$out .= $k . '="' . $v . '"'`), the JSON `"` around keys/values terminates the attribute and `JSON_HEX_APOS` does not help — verify `esc_attr()`/`htmlspecialchars()` wraps the encoded value before concatenation.
17. **Allowlist-constrained sources are not user-injectable for HTML.** A value drawn only from a developer-defined lookup or a validated control type cannot inject markup — confirm the specific variable comes exclusively from the constrained source.
   - WooCommerce `WC()->countries->countries[$code]`/`get_states($code)` return safe strings keyed by ISO code; the raw `get_billing_state()` fallback (no map entry) IS attacker-controlled and needs `esc_html()`.
   - Elementor SELECT/SWITCHER/SLIDER/COLOR controls are developer allowlists — only TEXT/TEXTAREA accept arbitrary input (classify via `add_control()`/`_register_controls()` in the same class).
   - A CSS integer gated by `is_numeric()`/`ctype_digit()` before a `<style>` block rejects `;`/`}` breakout — confirm the gate fires on the exact variable and non-numeric input yields a safe default.
   - Underscore `<%= %>`/Handlebars `{{{ }}}` raw interpolation is safe when every served value passed `sanitize_text_field()`/`strip_tags()` (deletes `<`) on both write and read paths. The companion single-brace `{{ }}` form in a `wp.template()`-compiled Underscore template is HTML-escaped automatically via `_.escape()` at render time regardless of write-time sanitization — only the triple-brace/no-escaping forms need the write-path check.
   - `"` in `<option value="...">` inside a native `<select>` does not fire `onmouseover`/`onfocus`/`onclick`; dismiss unless a JS library renders option values via `.html()` (not Select2's `.text()` — see rule 23).
   - A field programmatically truncated to ≤2–3 characters before reaching an unescaped HTML/attribute sink (e.g. initials/avatar-letter generation) cannot carry a functional injection payload — minimum viable event-handler/attribute-breakout injection needs more characters; verify the truncation is unconditional and applied before the sink.
   - SVG content embedded via an `<img src>` tag (not inline `<svg>`, `<object>`, or `<embed>`) is rendered as a static raster image by all major browsers — embedded `<script>`/event-handler markup inside it does not execute; this applies only to the `<img>`-loading method.
18. **TP — `$wp_query->get()` from rewrite rules.** Injectable when a percent-encoded URL prefix forces `parse_request()`'s `urldecode()` fallback (class-wp.php:239); verify the plugin passes the value into raw SQL without `$wpdb->prepare()`.
19. **`do_shortcode()`/`apply_shortcodes()` with user-controlled input.** No shortcode-name allowlist → arbitrary shortcode execution (a nonce authorizes the visit, not which names may run); `apply_shortcodes()` is a Core alias (shortcodes.php:223).
   - FP for the standard `the_content` chain (Core registers `do_shortcode` at priority 11) when the source is a published post's `post_content` written via normal Contributor+ editing — TP only when the content is writable by a lower-privilege role, or `do_shortcode()` runs on user input outside the `the_content` chain.
20. **Escaping applied at a later line/frame, not the concat site.** For a flagged tag/class/style/attribute concat (Semgrep `block-attribute-string-concat-tag-name`, `block-attribute-class-attr-concat`), check whether the FULL composed string is wrapped (`esc_attr()`/`esc_url()`/`esc_html()`) at the insertion site — even a different line/frame or a getter escaping inside its own `return` (e.g. `acf_esc_html()`) — or whether the value passed a `ctype_alnum()`/`absint()`/allowlist/`switch`-literal check before the concat; either neutralizes it.
21. **TP — attacker string into an `href`/`src`/`action` attribute; the escaper must fit the context.** Raw `$var` in a double-quoted attribute (`INTERPOLATED_HREF_ATTR_NO_ESC` + Semgrep `string-concat-url-attr-no-esc-url`), JS-side `'<a href="'+url+'">'` re-parsed incl. `.attr('href')` read-back (`JS_HREF_SRC_ATTR_STRING_CONCAT` + Semgrep `href-url-string-concat`), and `addcslashes($url,'/')` as sole escaper (escapes only `/`, not `"<>`; `ADDCSLASHES_SLASH_ONLY_HTML_INJECT`) are all live.
   - Not a sink when the value is freshly rebuilt from a whitelisted/regex-stripped token, or a context-correct escaper runs — including via an object-method wrapper (`$obj->escUrl()`/`$obj->escAttr()`, a common DI-facade pattern around WP core functions) rather than the bare global, which a text grep for `esc_url(`/`esc_attr(` alone will miss — or jQuery `.attr(k,v)`/`$('<tag/>',{})` which set the DOM node directly; the `addcslashes` case becomes live when the URL was `html_entity_decode(stripslashes())`'d from stored `\uXXXX` escapes.
   - `esc_url_raw()`/`sanitize_url()` is NOT a context-correct escaper for a single-quoted attribute (→ Chain 13) — unlike `esc_url()`'s default `'display'` context, it never HTML-entity-encodes `'`; confirm which of the two the code actually calls, and which quote character delimits the attribute, before dismissing an `href`/`src` sink as safe.
22. **TP — sanitizer skipped by input shape.** A custom sanitizer that raw-returns on an allow-listed key (`SANITIZER_KEY_ALLOWLIST_BYPASS` + Semgrep `sanitizer-key-allowlist-bypass`), or only sanitizes under `is_string($value)` with no `elseif (is_array($value))` sibling — bypassed by `field[]=x` (`IS_STRING_ONLY_SANITIZER_ARRAY_BYPASS` + Semgrep `is-string-only-sanitizer-array-bypass`) — leaves the value unsanitized. Confirm an in-scope role controls the key/shape, a render path echoes the survivor, and check EVERY sibling loop (partial fixes leave one untouched).
23. **TP — Select2/autocomplete `escapeMarkup` overridden to identity** plus a `templateResult`/`formatResult` concatenating an AJAX field into markup renders it as live HTML (`SELECT2_ESCAPE_MARKUP_OVERRIDE`; PHP side `json-encode-echo-unsanitized`) — the counter-case to the native-`<select>` `<option>` safety (rule 17). Confirm the field is DB-backed and writable by an in-scope role and that any per-element server escaper actually changed the value (not a no-op reference bug).
24. **Third-party/API-response fields echoed unescaped — verify origin.** Provider-generated response fields (payment status enums, risk scores, brand/last4, provider IDs) are FP for XSS unless a lower-privilege feature lets a user influence that SPECIFIC field at the outbound-request stage — the converse of `WC_BILLING_FIELD_READS` (customer-submitted billing/shipping getters stay tainted).
   - **Remote script/widget inclusion is a separate, more severe class than field-echo XSS.** A `<script src=...>`/iframe `src` built from a provider/account identifier stored via `get_option()` can be fully correct from an escaping standpoint (`esc_url()`/`esc_attr()` prevent tag/attribute breakout) while still loading fully attacker-authored JavaScript, because escaping the URL's syntax does not constrain the CONTENT of the file it points to. Check whether that identifier is writable by a lower-privileged actor via a SEPARATE handler (e.g. a missing-auth/CSRF option write) before scoring this sink's escaping as sufficient — if it is, classify as CWE-829 unconstrained script inclusion, not bounded field-value injection.
25. **POI & object-projection sinks.** `maybe_unserialize()` is a POI sink — `__wakeup`/`__destruct` fire DURING `unserialize()` before the `is_serialized()` guard helps; trace ALL write paths to the same column.
   - `(array)$user` exposes `data->user_pass` — verify an explicit key allowlist before projecting a user object.
